# USE: Wrap Tools Behind MCP, and Prove Limits + Audit

**Tier 8 - USE.** In BUILD you wrote a safe, auditable agent. These two exercises reinforce the two ideas at the center of this tier: **MCP** (serving tools over a standard protocol) and **the safety controls** (limits and the audit trail). Both run entirely on the mock model - **no API key needed**.

**Prerequisite:** you finished BUILD (`~/project8-db-ops-agent` exists, the agent runs). You have read Concepts 8.4 (MCP) and 8.5 (safety).

You will:
1. Wrap two of the agent's tools behind an **MCP server** and connect the agent to it, so those tools are served over the protocol instead of called directly.
2. Add and demonstrate **spending limits, tool-call limits, and an audit trail**, and produce a **sample audit log**.

## Exercise 1: Serve two tools over MCP and connect the agent

The agent's read-only tools are ordinary Python functions today. In this exercise you put two of them - `get_db_health` and `search_runbooks` - behind a **local MCP server** (Concepts 8.4: local stdio transport, no network), and have the agent call them through an **MCP client**. Same agent, same harness; the two tools now cross the MCP protocol.

The project already ships three small files that make this concrete:
- `mcp/mcp_server.py` - a minimal MCP-style server that exposes the two read tools over stdio.
- `mcp/mcp_client.py` - a minimal MCP client that launches the server as a subprocess and calls it.
- `use_mcp_agent.py` - a driver that points the agent's two read tools at the MCP client, then runs the agent.

### Step 1: See what the MCP server offers

On your **lab server** (CentOS Stream 9), as **ec2-user**, from the project folder:

```bash
cd ~/project8-db-ops-agent
```

Run the MCP client's built-in demo. It launches the server and lists its tools:

```bash
python3 mcp/mcp_client.py
```

`python3` runs the file. The client starts `mcp_server.py` as a subprocess and talks to it over stdin/stdout - the local transport from Concepts 8.4.

Expected output:

```
Tools offered by the MCP server:
  - get_db_health: Return current DB health metrics (cpu_pct, connections, max_...
  - search_runbooks: Search operational runbooks for a keyword. Read-only. Use to...

Calling get_db_health(instance='pg-prod-1') over MCP:
   {"cpu_pct": 95, "connections": 480, "max_connections": 500, "replication_lag_s": 42}
```

The metrics came back **over the MCP protocol**, not from a direct Python call. That is the whole idea: a tool built once behind an MCP server can be used by any MCP-capable agent.

### Step 2: Run the agent with its tools served over MCP

Now run the agent so its two read tools go through the MCP client:

```bash
python3 use_mcp_agent.py
```

Expected output:

```
MCP server offers: ['get_db_health', 'search_runbooks']
[auto-approve] approving action 'recommend_action'

===== AGENT (tools over MCP) RESULT =====
stopped because: model_done   tool calls: 3
----- final answer -----
INCIDENT REPORT (generated by db-ops agent)
- pg-prod-1 health: cpu=95% connections=480/500 replication_lag=42s
- FINDING: CPU is critically high (>=85%).
- FINDING: replication lag is high (>=30s).
- RECOMMENDED (needs human approval): investigate top queries and consider read-replica failover [recommendation_recorded]
- No destructive command was executed. All actions require human approval.
```

The report is identical to the BUILD run - but `get_db_health` and `search_runbooks` were served by the MCP server this time. The agent did not care where the tools lived; it just called them. That is the payoff of a standard protocol.

### Step 3: Read how the wiring works (open the files with vi)

Look at the driver to see exactly how the two tools were pointed at MCP:

```bash
vi use_mcp_agent.py
```

The key lines replace the agent's local functions with calls that go over the client:

```python
agent.TOOLS["get_db_health"] = lambda instance: client.call_tool("get_db_health", {"instance": instance})
agent.TOOLS["search_runbooks"] = lambda query: client.call_tool("search_runbooks", {"query": query})
```

That is the entire change - the harness, the loop, the approval gate, the audit are untouched. To leave vi without editing, type `:q` and press Enter.

Then skim the server to see the request/execute boundary and the allowlist (it exposes only the two read tools, never the action tool):

```bash
vi mcp/mcp_server.py
```

Note `EXPOSED` - the server deliberately offers only `get_db_health` and `search_runbooks`. Even over MCP, the action tool is not on the wire. To leave vi, type `:q` and press Enter.

**What you learned:** MCP lets you serve a tool once and reuse it across agents; the local stdio transport needs no network; and the server itself is an allowlist boundary - it exposes only the tools you choose.

## Exercise 2: Prove the limits and produce a sample audit log

The agent already has three safety controls from BUILD: a **tool-call limit**, a **token budget**, and an **audit trail**. This exercise makes them visible and produces a sample audit log you could hand a client.

### Step 1: Produce a clean audit log from a normal run

Still as **ec2-user**, in `~/project8-db-ops-agent`, run the agent once (auto-approving the action) so it writes a fresh audit log:

```bash
python3 agent.py --auto-approve
```

This writes `audit.log`. Now summarize it with the report helper:

```bash
python3 audit_report.py
```

`audit_report.py` reads the JSON-lines audit trail and prints a tidy summary.

Expected output:

```
===== AUDIT REPORT =====
goal:            Check the health of pg-prod-1 and write an incident report.
limits:          max_tool_calls=8 max_tokens=20000
tool calls:      3
  - get_db_health    ok
  - search_runbooks  ok
  - recommend_action ok
actions approved: 1
actions denied:   0
unknown tools refused: 0
run ended:       final
========================

```

This summary is your **sample audit log** deliverable: it shows the goal, the limits that were in force, every tool call and its result, and how the run ended. It answers "what did the agent do?" at a glance.

### Step 2: Prove the tool-call limit actually bites

Now force the limit to fire. The tool-call cap is read from the environment variable `AGENT_MAX_TOOL_CALLS`. Set it to `2` for one run:

```bash
AGENT_MAX_TOOL_CALLS=2 python3 -c "import agent; agent.reset_audit(); r=agent.run('demo low limit', approver=lambda n,i: True); print('stopped:', r['stopped'], 'calls:', r['tool_calls'])"
```

Putting `AGENT_MAX_TOOL_CALLS=2` in front of the command sets that variable for just this run. The one-liner runs the agent and prints why it stopped.

Expected output:

```
stopped: max_tool_calls calls: 2
```

The agent hit the cap after two tool calls and stopped - it did not finish the report, because the limit fired first. Look at the audit log for this run:

```bash
python3 audit_report.py
```

Expected output:

```
===== AUDIT REPORT =====
goal:            demo low limit
limits:          max_tool_calls=2 max_tokens=20000
tool calls:      2
  - get_db_health    ok
  - search_runbooks  ok
actions approved: 0
actions denied:   0
unknown tools refused: 0
run ended:       max_tool_calls
========================

```

`run ended: max_tool_calls` - the audit trail records not just what the agent did, but *why it stopped*. That is exactly what you want when investigating a truncated run.

### Step 3: Prove the token budget bites too

The token budget is `AGENT_MAX_TOKENS`. Set it very low so the budget stops the run before the tool-call cap:

```bash
AGENT_MAX_TOKENS=50 python3 -c "import agent; agent.reset_audit(); r=agent.run('demo low budget', approver=lambda n,i: True); print('stopped:', r['stopped'], 'tokens:', r['tokens_used'])"
```

Expected output (the token count will differ slightly on your machine):

```
stopped: budget_exhausted tokens: 71
```

The spending limit stopped the run once the estimated tokens crossed the budget. In production this is your guard against a runaway agent draining money - the same control SURVIVE's infinite-loop scenario drills.

**What you learned:** the two limits are real termination conditions, not decoration - each one stops the loop and is recorded in the audit trail with a clear reason. The audit report turns raw JSON lines into a summary a client (or an auditor) can read: the goal, the limits, every tool call, and how the run ended.
