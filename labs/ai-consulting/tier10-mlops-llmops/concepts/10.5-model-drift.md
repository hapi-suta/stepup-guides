# Concepts 10.5: Model drift

**Tier 10 - MLOps and LLMOps (ai-consulting track).** A teaching reference. Read it before BUILD.

A model is trained on a snapshot of the past. The world keeps moving. **Drift** is the gap that opens between the world the model learned and the world it now runs in. Drift is why a model that was accurate at launch quietly gets worse, and why "deploy and forget" is the most expensive mistake in production AI.

The critical property of drift is that it is **silent**. The model keeps returning answers. The API keeps returning HTTP 200. Nothing errors. The predictions just get less right, week by week, until someone notices the business outcome slipping. Drift detection is how you catch it before that.

---

## The kinds of drift

The plan lists several. They are distinct, and a consultant should name the right one.

### Data drift

**Data drift** is a change in the distribution of the model's inputs. The features the model sees no longer look like the features it trained on. Example: a fraud model trained before a new payment method launches now sees transaction patterns it never learned. The relationship between inputs and outputs may be unchanged - it is the inputs that moved.

You detect data drift by comparing the live feature distribution against the training baseline using a statistical test. In BUILD you use the two-sample Kolmogorov-Smirnov (KS) test. Precisely: its null hypothesis is that the two samples are drawn from the same distribution; the test statistic D is the largest absolute gap between the two samples' empirical cumulative distribution functions (ECDFs); a large D produces a small p-value, which is evidence against the null - that is, the live data no longer matches the training data (see: https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.ks_2samp.html). This runs in plain Python with `scipy.stats.ks_2samp`, offline, per feature.

Two caveats a consultant should state, not gloss over. First, the KS test is defined for **continuous** distributions - it is the right tool for numeric features, but it is not appropriate for categorical features (for those, use a chi-square or a population-stability-index style check instead). Second, the p-value is sensitive to sample size: on very large live batches, tiny, operationally-meaningless differences can still produce a small p-value, so pair the p-value with the effect size (the D statistic) and a business-set threshold rather than treating "p < 0.05" as automatic action.

### Concept drift

**Concept drift** is a change in the relationship between inputs and outputs - the meaning of the pattern changed. The inputs might look the same, but what they imply is different. Example: before a recession, "spending down 10%" meant one thing; during a recession it means another. The model's learned rule is now wrong even though the inputs are familiar. Concept drift usually shows up as falling accuracy on freshly labelled data, because you need to know the true outcomes to see that the rule broke.

The distinction interviewers probe: **data drift = the inputs changed; concept drift = the meaning changed.** Data drift you can spot from inputs alone; concept drift you generally need labels to confirm.

### Performance drift

**Performance drift** is the bottom line: the model's measured quality (accuracy, F1, groundedness) is falling on recent data. It is the symptom that data drift or concept drift produces. If you have labels, tracking performance drift directly is the strongest signal. If you do not have fresh labels yet, data-drift detection is your early warning.

### Prompt drift

**Prompt drift** is the LLMOps version: the app's quality falls because the **prompt** changed, not the data. Someone edited the system prompt to fix one case and degraded others; or a prompt template accumulated tweaks until it no longer produces the format the app expects. You catch prompt drift with the prompt regression test from Concepts 10.4 - the golden set fails when a prompt edit breaks known-good cases. The prompt-drift SURVIVE scenario in this tier makes this concrete.

### Knowledge-base decay

For a RAG app, **knowledge-base decay** is the documents going stale: policies change, products are discontinued, but the vector store still holds the old versions. The retrieval works fine; it just retrieves outdated truth. You manage it with a document-refresh process and by tracking document age and version in the store.

### Model-provider changes and embedding-model changes

Two LLMOps-specific drifts caused by the vendor, not your data:

- **Model-provider changes:** the vendor updates or deprecates the model version behind your app. Behaviour shifts under you even though your code did not change. You manage this with model versioning and a registry-based cutover (the provider-deprecation SURVIVE scenario).
- **Embedding-model changes:** if you change the embedding model, old vectors and new vectors are no longer comparable, so retrieval silently degrades. Changing embeddings means re-indexing everything. This is a common, painful, real-world incident.

## Threshold alerts

Detection is only useful if it triggers action. A **threshold alert** fires when a drift metric crosses a line you set in advance - for example, "alert if any feature's KS p-value drops below 0.01," or "alert if weekly accuracy falls more than 5 points," or "alert if the prompt regression suite fails." The threshold turns a chart into an action. In BUILD your drift detector exits non-zero when drift crosses the threshold, which lets a monitor or a retrain job react automatically.

Set thresholds deliberately: too tight and you get alert fatigue and needless retraining; too loose and drift runs for weeks before you notice. Tuning the threshold is a judgement call you make with the business, based on the cost of a wrong prediction.

---

## Responding to drift: retrain or retire

Detecting drift is half the job. The response is a decision, not a reflex:

- **Retrain** on fresh, correctly labelled data when the use case is still valid and the drift is a data or performance change you can fix by relearning.
- **Retire** when the world has changed so much that the use case no longer holds, or when retraining will not help (for example, the thing you were predicting no longer exists).
- **Do nothing yet** when the drift is within tolerance - not every wobble deserves a retrain, which costs money and risks a worse model.

The consulting maturity signal is that you retrain **because a signal told you to**, and you can show the signal. Blindly retraining every month is not MLOps; it is a habit.

---

## Key terms recap

- **Drift:** the gap between the world the model learned and the world it runs in; silent by default.
- **Data drift:** the input distribution changed. Detect with a statistical test (KS) on inputs.
- **Concept drift:** the input-to-output relationship changed. Usually needs labels to confirm.
- **Performance drift:** measured quality is falling - the symptom of the above.
- **Prompt drift:** LLM quality falls because the prompt changed; caught by prompt regression.
- **Knowledge-base decay:** RAG documents go stale.
- **Model-provider / embedding-model changes:** vendor-driven drift; version and re-index to manage.
- **Threshold alert:** fires when a drift metric crosses a preset line; turns detection into action.
- **Retrain vs retire:** the deliberate response to confirmed drift.
