# Concepts 10.3: LLMOps - operating an LLM application

**Tier 10 - MLOps and LLMOps (ai-consulting track).** A teaching reference. Read it before BUILD.

LLMOps is MLOps for applications built on large language models. Everything from Concepts 10.1 still applies - you version, deploy, monitor, and roll back. But an LLM app has failure modes a classical model does not, and it costs money per request in a way a classical model does not. LLMOps is the extra operational layer that handles those differences.

The single sentence to remember: **a classical model can be wrong; an LLM app can be wrong, expensive, unsafe, and inconsistent all at once, and it can change under you when the vendor updates the model.** LLMOps is how you keep that under control.

---

## Why an LLM app is different

A classical model like the Tier 4 incident classifier is a fixed function you trained and own. You control it completely. An LLM app is different in five ways:

1. **You often do not own the model.** It runs at a vendor (Anthropic, OpenAI, a cloud host). The vendor can deprecate a version, change behaviour, have an outage, or raise prices.
2. **Every request costs money**, priced per token. A runaway loop is not just a bug - it is a bill.
3. **The output is free text**, so "correct" is fuzzy. There is no single accuracy number.
4. **It can be unsafe**: it can hallucinate, leak data, or be manipulated by injected instructions.
5. **The same input can give different outputs** because of sampling. Consistency itself is something you must monitor.

Because of this, an LLM app needs a wider monitoring surface than a normal web app.

---

## What you monitor for an LLM app

The plan lists exactly what to watch. Here is each, and why it matters.

- **Requests:** volume over time. A sudden spike may be legitimate load or an abuse/loop problem.
- **Token usage:** input and output tokens per request. Tokens are the unit of cost and the unit of the context window. Rising tokens mean rising cost.
- **Model cost:** the dollar figure, derived from tokens times price. One precision point that trips people up: input tokens and output tokens are priced separately, and output is typically several times more expensive than input (verify current per-model rates in the provider's pricing docs). So cost is (input tokens x input price) + (output tokens x output price), plus any cache-read/cache-write adjustments - not a single blended rate. This is the number a client's finance team cares about. You must be able to show it live.
- **Response time (latency):** LLM calls are slow compared to a classical model. Latency drives user experience and can indicate provider trouble.
- **Error rate:** failed calls - timeouts, 429 rate limits, 5xx from the provider. A rising error rate often means a provider incident.
- **Prompt versions:** which version of the prompt template produced each response. When quality changes, the first question is "did the prompt change?" You cannot answer it without prompt versioning.
- **Model versions:** which model (and which model version) served each request. Vendors update models; behaviour shifts. You need to know which version was live when.
- **Retrieval performance:** for a RAG app (Tier 7), whether retrieval returned the right chunks. Bad retrieval is a top cause of bad answers.
- **Groundedness:** whether the answer is actually supported by the retrieved sources, or whether the model made it up. This is the LLM-specific quality metric.
- **Safety violations:** refusals that should not happen, or unsafe outputs that should have been refused. Both are signals.
- **User feedback:** thumbs up/down and corrections. Cheap, direct signal of real-world quality.
- **Tool-call accuracy:** for an agent (Tier 8), whether the model called the right tool with the right arguments.
- **Vendor outages:** provider availability. When the provider is down, your app is down unless you have a fallback (Tier 6).

A normal web app monitors roughly the first five (requests, latency, errors, and infra). Everything from prompt versions down is LLM-specific. When an interviewer asks "what do you monitor for an LLM app that you would not for a normal web app," the answer is that list: tokens, cost, prompt/model versions, groundedness, safety, tool-call accuracy, and vendor status.

## Prompt versioning

A prompt is code. It changes behaviour, so it must be versioned like code. Concretely:

- Store prompt templates in files under source control, not pasted into the app.
- Give each a version identifier, and log which version produced each response.
- Never edit a live prompt without running it against a golden test set first (see Concepts 10.4).

The reason is **prompt drift** (Concepts 10.5): someone tweaks a prompt to fix one case and silently breaks ten others. Without versioning and a regression test, you find out from an angry customer.

## Cost control

Cost is a first-class operational concern in LLMOps, not an afterthought. The controls:

- **Token counting** on every request so you can see and cap usage.
- **Budgets and alerts**: a threshold that fires when spend or volume crosses a line, so a 2am runaway does not become a five-figure surprise.
- **Caching**: two different things go by this name, and a consultant should not blur them. (1) *Application-level response caching* - if the exact same request appears repeatedly, serve a stored answer instead of calling the model again. (2) *Provider prompt caching* - a feature offered by major LLM APIs (for example Anthropic's prompt caching) that stores a large, repeated prompt *prefix* server-side so the shared portion is billed at a steep discount on later calls; cache reads are roughly a tenth of the normal input-token price, and cache writes carry a small premium (verify current numbers and TTLs in the provider docs, see: https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching). Prompt caching cuts the cost of the *repeated context* (a long system prompt, retrieved docs); it does not return a canned answer.
- **Batching** where the workload allows. Some providers also offer an asynchronous batch mode (for non-latency-sensitive jobs) at a reduced per-token price - verify current discounts in the provider docs.

In BUILD and USE you log tokens and cost per request and wire a cost alert that fires when a budget is breached. The cost-alert SURVIVE scenario proves it holds under a runaway.

## Groundedness

For a RAG assistant, groundedness is the metric that separates a useful answer from a confident lie. An answer is grounded if every claim in it is supported by the retrieved source documents. You measure it by checking the answer's claims against the retrieved context - by rule, by a scoring model, or by human review. Low groundedness means the model is hallucinating, and for an enterprise client that is the difference between a tool they trust and a liability.

---

## Key terms recap

- **LLMOps:** MLOps plus the extra controls an LLM app needs - cost, safety, consistency, vendor management.
- **Token usage / model cost:** tokens are the unit of both cost and context; cost is tokens times price.
- **Prompt versioning:** treating prompts as versioned code, logged per response.
- **Model versioning:** knowing which model and version served each request.
- **Groundedness:** whether the answer is supported by its sources.
- **Safety violations:** wrong refusals or unsafe outputs.
- **Tool-call accuracy:** whether an agent called the right tool correctly.
- **Vendor outage / deprecation:** the provider risk that classical models do not have.
