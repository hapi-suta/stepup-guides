# Concepts 10.2: The MLOps and LLMOps toolbox

**Tier 10 - MLOps and LLMOps (ai-consulting track).** A teaching reference. Read it before BUILD.

You do not need to master every tool below to be a consultant. You need to know what each one is for, where it sits in the lifecycle from Concepts 10.1, and when you would recommend it. A client will ask "what stack do we need?" and expect a clear, opinionated answer that is not just a list of logos.

The plan lists these tools: MLflow, Docker, Kubernetes fundamentals, GitHub Actions, Terraform, Airflow, Prometheus, Grafana, OpenTelemetry, feature-store concepts, and model-serving platforms. Here is what each does and how they fit together.

In this tier you build lightweight, offline stand-ins for the heavy tools so you understand what they store and why. Once you understand the concept, swapping in the real product is a configuration exercise, not a mystery.

---

## Tracking and registry

### MLflow

MLflow does two of the lifecycle jobs: **experiment tracking** and the **model registry**. You log runs (params, metrics, artifacts) and it stores them so you can compare runs and see history (see: https://mlflow.org/docs/latest/ml/tracking/). Its registry lets you mark which model version is the current production one and move that pointer over time (see: https://mlflow.org/docs/latest/ml/model-registry/).

One currency note: MLflow's original fixed **stages** (`Staging`, `Production`, `Archived`) are deprecated and being replaced by **model version aliases** and tags (for example a `champion` alias), which are more flexible. The idea is identical - a named pointer to the live version - the API just moved from stages to aliases. Confirm the current mechanism in the MLflow docs before configuring a client's registry.

In BUILD you build a file-and-SQLite version of exactly this: `experiments.jsonl` for tracking and a `registry.db` table with a `stage` column. When you later point a client at real MLflow, you already understand what the buttons do.

### Feature-store concepts

A feature store is a shared, versioned place to compute and serve the input features a model needs, so training and serving use the same feature definitions. The failure it prevents is **training/serving skew**: the feature is computed one way in the notebook and a subtly different way in production, so the live model quietly underperforms. You do not need to run a feature store in this tier; you need to be able to explain the skew problem it solves.

## Packaging and running

### Docker

Docker packages your model, its code, and its exact dependencies into an image that runs the same on your laptop, a server, or the cloud. It is the answer to "it worked on my machine." A model API almost always ships as a Docker image. You already met Docker in Phase 0; here it is the deployment unit.

### Kubernetes fundamentals

Kubernetes runs and scales many containers across many machines, restarting them when they die and routing traffic to healthy ones. You do not need to be a Kubernetes expert to consult on AI. You need to know it is the platform that gives you scaling, self-healing, and rolling deploys for containerised model services - and that it is heavy, so a small deployment may not need it.

### Model-serving platforms

These are purpose-built ways to serve models behind an API with batching, versioning, and metrics built in - for example a hosted endpoint on a cloud platform, or an open-source server. In BUILD you serve with FastAPI, which is the plain, transparent version of what these platforms wrap.

## Automation and infrastructure

### GitHub Actions

GitHub Actions is CI/CD: it runs your tests, your prompt-regression checks, and your build-and-deploy steps automatically whenever code changes. It is the gate that stops a broken model or a bad prompt from shipping. In this tier the CI concept is central - the proof of competence requires that a deliberately bad prompt is blocked by a CI gate.

### Terraform

Terraform is **infrastructure as code**: you describe your servers, networks, and cloud resources in text files, and Terraform creates them exactly and repeatably. The value is that your infrastructure is versioned, reviewable, and reproducible - the same discipline as dataset versioning, applied to servers. If a region burns down, you re-run Terraform.

### Airflow

Airflow schedules and orchestrates pipelines - the "run these steps in this order, on this schedule, and alert me if a step fails" engine. It is how the train-to-register pipeline from Concepts 10.1 runs reliably overnight. In this tier a cron job plus your retrain script is the miniature version.

## Monitoring and observability

### Prometheus

Prometheus collects numeric metrics over time - request count, latency, tokens, cost, error rate - and stores them as time series. Its default collection model is **pull**: Prometheus scrapes an HTTP metrics endpoint your service exposes, at a regular interval (see: https://prometheus.io/docs/introduction/overview/). Newer Prometheus can also receive pushed metrics over OTLP, but scraping is the model to know. It is the database of "what happened, minute by minute."

### Grafana

Grafana draws the dashboards on top of Prometheus. It is what a client actually looks at: graphs of cost, latency, and groundedness over time, with alert thresholds drawn on. In USE you wire a Prometheus-and-Grafana-style dashboard for your LLM app.

### OpenTelemetry

OpenTelemetry (OTel) is a vendor-neutral, open standard and toolkit for emitting the three signals of telemetry - traces, metrics, and logs - from your application, so you are not locked into one monitoring vendor (see: https://opentelemetry.io/docs/what-is-opentelemetry/). The consulting point is portability: instrument once with OpenTelemetry and you can export the data to any compatible backend (including Prometheus for metrics).

## How they fit together

Read this as one sentence per lifecycle stage:

- **Track and register** your runs with MLflow.
- **Package** the winning model with Docker.
- **Run and scale** it with Kubernetes or a model-serving platform.
- **Automate** the pipeline with Airflow and gate deploys with GitHub Actions.
- **Provision** the infrastructure reproducibly with Terraform.
- **Monitor** it with Prometheus, visualise with Grafana, instrument with OpenTelemetry.

A consultant's job is not to install all eleven. It is to look at a client's size, skills, and risk, and recommend the smallest stack that covers the lifecycle. A three-person team does not need Kubernetes and Airflow; a bank running dozens of models does. Right-sizing the stack is the value you add.

## Key terms recap

- **MLflow:** experiment tracking plus model registry.
- **Feature store:** shared versioned features; prevents training/serving skew.
- **Docker:** packages code and dependencies into a portable image.
- **Kubernetes:** runs and scales containers, self-healing.
- **Model-serving platform:** purpose-built model API host.
- **GitHub Actions:** CI/CD gate for tests and deploys.
- **Terraform:** infrastructure as code, reproducible servers.
- **Airflow:** pipeline scheduling and orchestration.
- **Prometheus:** time-series metric collection.
- **Grafana:** dashboards on top of metrics.
- **OpenTelemetry:** vendor-neutral instrumentation standard.
