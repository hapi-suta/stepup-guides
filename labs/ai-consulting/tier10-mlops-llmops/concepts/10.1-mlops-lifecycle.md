# Concepts 10.1: The MLOps lifecycle

**Tier 10 - MLOps and LLMOps (ai-consulting track).** This is a teaching reference. Read it before you touch a keyboard in BUILD. It gives you the vocabulary a hiring panel and a client will expect you to use precisely.

MLOps is what turns a model that works in a notebook into a system a business can rely on. A model in a notebook is an experiment. A model behind an API that people trust with real decisions is a product. MLOps is the set of practices that gets you from the first to the second, and keeps it working after the data changes.

Think of it the way a DBA thinks about a database. You do not just create a table and walk away. You back it up, you monitor it, you version your schema changes, you have a rollback plan, and you know how to restore it. MLOps applies that same operational discipline to machine-learning models.

---

## The lifecycle stages

A model is never "done." It moves through a loop. These are the stages the plan lists, in plain language.

### 1. Experiment tracking

Every time you train a model you make choices: which data, which algorithm, which settings. You get a result: some accuracy number. If you do not write all of that down in a structured way, you cannot answer the most basic question a client will ask: "why is this the model we shipped, and not the other one?"

Experiment tracking means recording, for every training run: the input data version, the parameters, the code version (a git commit), and the resulting metrics. A tool like MLflow does this for you; in this tier you build a small file-based version so you understand what it actually stores.

### 2. Reproducibility

Reproducibility means that if you run the same training again, you get the same model. This sounds obvious and is constantly violated. The usual culprits are an unfixed random seed, a data file that quietly changed, or a library version that moved. If your result is not reproducible, it is not evidence - it is an anecdote. In BUILD you fix the random seed so your numbers match the guide exactly. That is reproducibility in miniature.

### 3. Model registry

The registry is the single source of truth for "which model is in production right now." It records each trained model, its metrics, and a label that tells you which version is the current production one. Deployment reads from the registry - it serves whatever the registry marks as production. This is what makes a controlled rollback possible: you flip the pointer back to the previous model instead of scrambling to rebuild it.

A note on how the label is expressed, because it changed. Older MLflow used fixed named **stages** (`Staging`, `Production`, `Archived`). Those stages are now deprecated and slated for removal; current MLflow steers you toward **model version aliases** (for example a `champion` alias) plus tags, which are more flexible - more than one alias can point at a version, which makes A/B testing and staged rollout easier (see: https://mlflow.org/docs/latest/ml/model-registry/). The concept is unchanged - a named pointer to "the one that is live" - only the mechanism moved from fixed stages to aliases. The BUILD `stage` column teaches the concept; verify the current API before you wire real MLflow for a client.

### 4. Dataset versioning

The data is part of the model. If you cannot say which exact dataset a model was trained on, you cannot reproduce it, audit it, or explain a regression. Dataset versioning means every training run points at an identifiable snapshot of the data - by hash, by date, or by a stored copy. Auditors and regulators care about this as much as the model itself.

### 5. Pipeline automation

A pipeline is the chain: get data -> prepare features -> train -> evaluate -> register. Automation means that chain runs the same way every time, triggered by a schedule or a code change, not by someone remembering to run seven scripts in the right order by hand. Automation removes the "it worked on my machine" failure mode.

### 6. Deployment

Deployment is putting the model behind something that can serve predictions - usually an API. The important MLOps idea is that deployment is decoupled from training: you train and register a model, and a separate step decides to serve it. That separation is what lets you roll back, run a canary, or shadow-test without retraining.

### 7. Validation

Before a model is allowed to serve real traffic, it must pass a gate: does it beat the current production model on the metric that matters? Does it pass the golden test set? Validation is the checkpoint that stops a worse model from shipping just because it is newer.

### 8. Monitoring

Once a model serves traffic, you watch it the way you watch any production system: request volume, latency, error rate. But you also watch things a normal web app never has - the distribution of the inputs and the quality of the outputs - because a model can keep returning HTTP 200 while quietly becoming wrong. Monitoring is how you find out before your client does.

### 9. Retraining

Models decay because the world changes (see Concepts 10.5 on drift). Retraining is refitting the model on fresh data. The mature practice is to retrain in response to a signal - measured drift or a performance drop - not on a blind fixed schedule. Retraining for no reason burns money and can make a model worse.

### 10. Rollback

Rollback is the ability to return to the last known-good model quickly and safely. Because the registry decouples "which model is production" from the model files, rollback is a pointer change, not a rebuild. Every production ML system must have a tested rollback. An untested rollback is a hope, not a plan.

### 11. Retirement

Eventually a model is replaced or the use case ends. Retirement means decommissioning it cleanly: stop serving it, archive it and its data for audit, and record why it was retired. This closes the loop responsibly.

## Why a consultant cares

A client executive does not want to hear about hyperparameters. They want answers to operational questions:

- Which model is live right now, and who approved it?
- If it goes wrong, how fast can we go back?
- How will we know it has gone wrong?
- Can we prove which data trained it, if a regulator asks?

Every one of those questions is answered by an MLOps practice above. When you can walk a client through this lifecycle and point at the artifacts that implement each stage, you are speaking as an implementation consultant, not a hobbyist.

---

## Key terms recap

- **Experiment tracking:** recording data, params, code version, and metrics for every run.
- **Reproducibility:** same inputs give the same model.
- **Model registry:** the source of truth for which model is in production.
- **Dataset versioning:** knowing exactly which data trained a model.
- **Pipeline automation:** the train-to-register chain runs the same way every time.
- **Deployment:** serving the model, decoupled from training.
- **Validation:** a gate that blocks a worse model from shipping.
- **Monitoring:** watching operational health and model quality in production.
- **Retraining:** refitting on fresh data, triggered by a signal.
- **Rollback:** returning to the last known-good model quickly.
- **Retirement:** decommissioning a model cleanly with an audit trail.
