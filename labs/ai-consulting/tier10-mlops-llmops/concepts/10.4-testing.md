# Concepts 10.4: Testing AI systems

**Tier 10 - MLOps and LLMOps (ai-consulting track).** A teaching reference. Read it before BUILD.

Testing an AI system is harder than testing ordinary software because the output is not a fixed value you can assert on. A function that adds two numbers has one right answer. A model that scores a ticket, or an LLM that answers a question, has a range of acceptable answers and a much larger range of wrong ones. This concept explains the layers of testing the plan lists, and what each one catches.

The goal is a gate: before any model or prompt reaches production, an automated test decides whether it is allowed to ship. That gate is the difference between "we hope it is fine" and "it passed the checks."

---

## Unit testing

Unit tests check the small, deterministic pieces around the model: the feature-preparation code, the input validation, the cost calculation, the API request shaping. These behave like normal software and should be tested like normal software. If your token-counting function is wrong, your whole cost dashboard is wrong - a unit test catches that. Unit tests do not test the model's quality; they test the plumbing.

## Integration testing

Integration tests check that the pieces work together: does a request flow through the API, hit the model, log a metric, and return a valid response? Does the deploy step load the model the registry marks as production? These tests catch wiring mistakes - the model loads but the API returns the wrong field, or the registry pointer is not read. In BUILD, hitting `/predict` and confirming a metric was logged is an integration test.

## Prompt regression testing

This is the LLM-specific heart of the tier. A **prompt regression test** runs a fixed set of prompts through the current prompt template and checks the answers still meet expectations. When someone edits a prompt, the regression test tells you whether the edit helped or quietly broke other cases.

The proof of competence for this tier requires that a deliberately bad prompt is blocked by a CI gate. That gate is a prompt regression test. In BUILD you build one: a golden set of questions, each with strings the answer must contain; if any case fails, the test exits non-zero and CI refuses to ship.

## Golden datasets

A **golden dataset** (or golden set) is a curated set of inputs with known-good expected outputs. It is the ground truth your regression tests measure against. For a classifier it is labelled examples; for an LLM app it is representative questions with the facts or citations the answer must include. The golden set must be:

- **Representative** of real traffic, including the hard and edge cases.
- **Stable**, so a change in the score means a change in the system, not the test.
- **Version-controlled**, because it is as important as the code.

A golden set is never finished. When a real failure slips through, you add it to the golden set so it can never regress again. That is how the safety net grows.

## Model comparison

When you have a candidate model or prompt, you compare it against the current production one on the same golden set and the same metric. Model comparison is what makes the validation gate objective: the new version ships only if it beats or matches the old one on the number that matters. "Newer" is not a reason to ship; "measurably better on the golden set" is.

## Load testing

Load testing sends many requests to see how the system behaves under volume: does latency stay acceptable, does the error rate climb, do you hit the provider's rate limit? For an LLM app, load testing also reveals cost under load - important before a launch. You want to discover the breaking point in a test, not in production.

## Red-team testing

Red-teaming is adversarial testing: you actively try to make the system misbehave - leak data, ignore its instructions, produce unsafe output, or run up cost. For an LLM app this includes prompt injection, jailbreaks, and attempts to extract the system prompt. Red-teaming is the security half of testing; Tier 11 goes deep on it. In this tier you should know it is a required test layer, not an optional one, for any customer-facing LLM app.

## Release strategies: canary and shadow

Two testing strategies happen in production, on a controlled slice of real traffic. Interviewers ask you to compare them.

### Canary release

A **canary** sends a small percentage of real traffic (say 5%) to the new version while the rest stays on the old one. You watch the canary's metrics. If it looks healthy, you ramp up to 100%; if it looks bad, you cut it back to 0% - an instant rollback affecting only a few users. Canary means the new version **does** serve some real users, but few of them, and you can pull it fast.

### Shadow testing

A **shadow** (or dark launch) sends real traffic to the new version **in parallel** but throws away its output - the user only ever sees the old version's answer. You compare the shadow's answers and metrics against production offline. Shadow means the new version serves **zero** real users; it is the safest way to test on real inputs because no user can be harmed by a bad shadow response. The trade-off is you pay for the extra calls and you cannot measure real user reactions.

Rule of thumb: **shadow** to check correctness on real inputs with zero user risk; **canary** to check real user impact with limited, quickly-reversible exposure. These are standard progressive-delivery patterns; the canary term comes from gradually shifting a slice of production traffic to a new version and rolling back fast if its metrics degrade (see: https://martinfowler.com/bliki/CanaryRelease.html), and shadow/dark-launch mirrors real traffic to the new version without surfacing its output to users (see: https://martinfowler.com/bliki/BlueGreenDeployment.html).

## Human evaluation

Some qualities cannot be checked by a rule - tone, helpfulness, subtle correctness. Human evaluation puts a person in the loop to rate outputs against a rubric. It is slow and expensive, so you use it on a sample and to build the golden set, not on every request. User feedback (thumbs up/down) is the cheap, continuous cousin of human evaluation.

---

## Key terms recap

- **Unit testing:** the deterministic plumbing around the model.
- **Integration testing:** the pieces working together end to end.
- **Prompt regression testing:** re-checking prompts against a golden set so an edit cannot silently break things.
- **Golden dataset:** curated inputs with known-good outputs; the ground truth for tests.
- **Model comparison:** candidate vs production on the same metric - the validation gate.
- **Load testing:** behaviour and cost under volume.
- **Red-team testing:** adversarial testing for safety and security.
- **Canary release:** small slice of real traffic to the new version, quickly reversible.
- **Shadow testing:** real traffic to the new version in parallel, output discarded, zero user risk.
- **Human evaluation:** people rating outputs against a rubric on a sample.
