PATRONI HA: CLASSROOM SETUP MANUAL
Prepared 9 September 2026

STUDENT: configure three etcd members, three PostgreSQL/Patroni members and
one HAProxy router. INSTRUCTOR: prepare and connect the Mattermost app server.

This manual is based on the SutaBot repository journey and configuration templates.
Expected results below are instructions for checking your work, not evidence that
these commands were run on new servers today. This file does not provision servers.

PART 0 — BEFORE CLASS
=====================
The main lesson assumes software, OS dependencies, service users, directories,
service units for Patroni/HAProxy/Mattermost, and TLS files are already installed.
The sysadmin reference at the end lists the existing installation procedure.
It requires Suta handoff artifacts; it is not a generic download/install guide.

Prepared versions: etcd 3.6.14+suta.2; PostgreSQL 16.15; Patroni 4.1.4;
HAProxy 3.2.22; Mattermost 11.10.1. Use the matching CentOS lab artifacts.

No database should have been initialized. Patroni will run initdb and clone the
replicas. All four application services should initially be stopped.

Fill in the private IPv4 address of each server:
  DCS_1_IP = __________________   (dcs-1)
  DCS_2_IP = __________________   (dcs-2)
  DCS_3_IP = __________________   (dcs-3)
  PG_HA_1_IP = __________________   (pg-ha-1)
  PG_HA_2_IP = __________________   (pg-ha-2)
  PG_HA_3_IP = __________________   (pg-ha-3)
  DB_ROUTER_1_IP = __________________   (db-router-1)
  MATTERMOST_1_IP = __________________   (mattermost-1)

Replace every *_IP token in the configuration text before saving it. These are
worksheet placeholders, not shell variables. Use actual private IPv4 addresses.
All eight hostnames must resolve to their correct private addresses.
Use the assigned terminal/SSH session for each named server as ec2-user.

Prepare three different strong passwords in a private password manager:
  REPLACE_POSTGRES_SUPERUSER_PASSWORD
  REPLACE_REPLICATION_PASSWORD
  REPLACE_MATTERMOST_DATABASE_PASSWORD
Use the same superuser and replication values on all three Patroni nodes.
For simple substitution in YAML and the application URI, use long random
alphanumeric passwords. Otherwise quote/escape YAML and percent-encode the URI
password correctly. Never use the literal placeholder as a password.

Network prerequisites within this lab: etcd peers 2380; etcd clients 2379;
PostgreSQL replication 5432; Patroni health API 8008 from the router;
app to router 5432; instructor access to Mattermost 8065 through the approved
lab access path. Do not expose PostgreSQL, etcd or the Patroni API to the internet.

TLS prerequisites: each etcd member certificate must cover that node's private
IP and hostname. Certificates must be current and signed by the same CA.
Patroni must have a client certificate and its matching private key.

How to use this file:
- Run one indented command at a time. Do not paste whole sections into a terminal.
- Text between BEGIN FILE and END FILE goes into the editor, not the shell.
- In vi: press i, paste the file text, press Escape, type :wq, press Enter.
- YAML indentation uses spaces. Keep the indentation shown.
- postgres=# is a database prompt; a prompt ending in $ is a Linux shell.
- Type only commands, never the sample prompt.
- Stop and investigate an unexpected result before the next dependency.

Check your starting terminal on every server:
    hostname

    whoami

Expect the assigned role name and ec2-user.

On each PostgreSQL server, verify the installed binary:
    /opt/pgsql/bin/postgres --version

Expect PostgreSQL 16.15. A version check proves the program runs, not that a
database has been created.

ARCHITECTURE
============
Mattermost -> HAProxy:5432 -> current PostgreSQL writer
Patroni on each PostgreSQL server -> etcd:2379 (mutual TLS)
etcd members -> each other:2380 (mutual TLS)
PostgreSQL writer -> streaming replicas

etcd stores coordination state and the leader lock; it does not store application
tables. Patroni manages PostgreSQL and leadership. HAProxy checks /primary on
port 8008 and sends database connections to the node reporting HTTP 200.
This lab uses asynchronous replication. It does not guarantee zero data loss.
A single router and a single app server remain single points of failure.

1. Configure dcs-1
-----------------------------------------------------------------
SERVER: dcs-1 | START AS: ec2-user in Linux

The first member needs a unique name, addresses, peer list, data directory and mutual-TLS rules.

    sudo vi /etc/systemd/system/etcd.service

The backslashes continue ONE ExecStart instruction across lines. They do not
chain commands. Keep them exactly as shown.

BEGIN FILE
[Unit]
Description=SUTA etcd member
After=network-online.target
Wants=network-online.target

[Service]
User=root
ExecStart=/usr/local/bin/etcd \
  --name=dcs-1 \
  --data-dir=/var/lib/etcd \
  --listen-client-urls=https://DCS_1_IP:2379 \
  --advertise-client-urls=https://DCS_1_IP:2379 \
  --listen-peer-urls=https://DCS_1_IP:2380 \
  --initial-advertise-peer-urls=https://DCS_1_IP:2380 \
  --initial-cluster=dcs-1=https://DCS_1_IP:2380,dcs-2=https://DCS_2_IP:2380,dcs-3=https://DCS_3_IP:2380 \
  --initial-cluster-state=new \
  --initial-cluster-token=suta-ha001-etcd \
  --client-cert-auth=true \
  --trusted-ca-file=/etc/etcd/ca.crt \
  --cert-file=/etc/etcd/member.crt \
  --key-file=/etc/etcd/member.key \
  --peer-client-cert-auth=true \
  --peer-trusted-ca-file=/etc/etcd/ca.crt \
  --peer-cert-file=/etc/etcd/member.crt \
  --peer-key-file=/etc/etcd/member.key
Restart=on-failure
RestartSec=5
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
END FILE

What happens: sudo opens the systemd unit with permission to save; vi lets you enter the exact role-resolved configuration supplied for this step.

Check:
    sudo grep -n "ExecStart" /etc/systemd/system/etcd.service

Look for: one ExecStart= line with the full path of the binary
grep -n prints matching lines with their line numbers. A saved unit file must contain exactly one ExecStart line; if grep prints nothing, the file was not saved or is empty.

Expected: vi opens the new etcd.service file; after saving, systemctl can parse the unit.

7. Prove quorum over mutual TLS
-----------------------------------------------------------------
SERVER: dcs-1 | START AS: ec2-user in Linux

A running process is weaker evidence than three reachable voting members that can commit.

    sudo /usr/local/bin/etcdctl --endpoints=https://dcs-1:2379,https://dcs-2:2379,https://dcs-3:2379 --cacert=/etc/etcd/ca.crt --cert=/etc/etcd/member.crt --key=/etc/etcd/member.key endpoint health

What happens: etcdctl contacts every named endpoint with the member certificate and asks each endpoint to commit a health proposal.

Expected: Three lines report healthy endpoints and successful proposal commits.

8. Configure Patroni on pg-ha-1
-----------------------------------------------------------------
SERVER: pg-ha-1 | START AS: ec2-user in Linux

Save this member’s generated identity and cluster configuration.

    sudo vi /etc/patroni/patroni.yml

BEGIN FILE
scope: suta-ha001
namespace: /service/
name: pg-ha-1
restapi:
  listen: PG_HA_1_IP:8008
  connect_address: PG_HA_1_IP:8008
etcd3:
  hosts: DCS_1_IP:2379,DCS_2_IP:2379,DCS_3_IP:2379
  protocol: https
  cacert: /etc/patroni/etcd-ca.crt
  cert: /etc/patroni/etcd-client.crt
  key: /etc/patroni/etcd-client.key
bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576
    postgresql:
      use_pg_rewind: true
      use_slots: true
      parameters:
        wal_level: replica
        hot_standby: 'on'
        max_wal_senders: 10
        max_replication_slots: 10
  initdb:
    - encoding: UTF8
    - data-checksums
  pg_hba:
    - local all all peer
    - host all postgres PG_HA_1_IP/32 scram-sha-256
    - host all postgres PG_HA_2_IP/32 scram-sha-256
    - host all postgres PG_HA_3_IP/32 scram-sha-256
    - host replication replicator PG_HA_1_IP/32 scram-sha-256
    - host replication replicator PG_HA_2_IP/32 scram-sha-256
    - host replication replicator PG_HA_3_IP/32 scram-sha-256
    - host mattermost mattermost DB_ROUTER_1_IP/32 scram-sha-256
postgresql:
  listen: PG_HA_1_IP:5432
  connect_address: PG_HA_1_IP:5432
  data_dir: /opt/pgsql/data
  bin_dir: /opt/pgsql/bin
  pgpass: /etc/patroni/pgpass
  authentication:
    superuser:
      username: postgres
      password: REPLACE_POSTGRES_SUPERUSER_PASSWORD
    replication:
      username: replicator
      password: REPLACE_REPLICATION_PASSWORD
  parameters:
    unix_socket_directories: /var/run/postgresql
    password_encryption: scram-sha-256
  create_replica_methods:
    - basebackup
  basebackup:
    checkpoint: fast
tags:
  nofailover: false
  noloadbalance: false
  clonefrom: false
END FILE

Check:
    sudo grep -n -E "^(scope|name|restapi|etcd3|postgresql):" /etc/patroni/patroni.yml

Look for: the scope, name, restapi, etcd3 and postgresql top-level keys, each on its own numbered line

WHEN A CHECK FAILS
=================
On the server with the failing service, read its recent logs. These are separate
commands; run the relevant one. Logs may contain sensitive configuration details.

    sudo journalctl -u etcd -n 80 --no-pager

    sudo journalctl -u patroni -n 80 --no-pager

    sudo journalctl -u haproxy -n 80 --no-pager

    sudo journalctl -u mattermost -n 80 --no-pager

Read from the earliest error in the failed start, not only the final exit line.
- etcd: certificate expired/unknown authority means check validity and common CA.
  Address/SAN mismatch means the certificate does not identify this server.
  Connection refused means check peer address, listener and network rules.
- Patroni: YAML errors identify an indentation or syntax problem. Permission
  denied often points at config, TLS keys, socket directory or the data directory.
  DCS connection errors must be fixed before PostgreSQL leadership can work.
- HAProxy: configuration validation gives a line number. If all backends are DOWN,
  inspect Patroni /primary health responses and port 8008 connectivity.
- Mattermost: password authentication failed means compare the role password with
  the URI. Connection refused means verify router listener and healthy backend.
Do not delete data directories or reset etcd to hide a configuration error.

UNDERSTAND THE IMPORTANT SETTINGS
=================================
scope and namespace identify the same Patroni cluster on all three nodes.
name is unique per node; connect_address advertises a reachable private address.
ttl=30 is the DCS leader-lock lifetime; loop_wait=10 is the normal control-loop
interval; retry_timeout=10 bounds retries. These are related settings.
maximum_lag_on_failover=1048576 excludes excessively lagging candidates by this
lag check; it is not a promise that at most 1 MB can ever be lost.
use_pg_rewind allows a former primary to be realigned when rewind prerequisites
hold. data-checksums is enabled at bootstrap to support this setup.
use_slots helps retain WAL needed by replicas; monitor WAL/disk if one is offline.
bootstrap.dcs seeds shared settings only when the cluster is first initialized.
Changing that section later does not automatically update existing DCS settings.
pg_hba permits local peer login, exact database-node addresses for administration
and replication, and the router address for the Mattermost role/database.
HAProxy /primary checks distinguish the writer from a merely reachable database.
The etcd snapshot is coordination metadata, not a PostgreSQL backup.
