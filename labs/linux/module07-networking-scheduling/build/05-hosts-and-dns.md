# Build 05: Hosts File and DNS

You will learn how a Linux server turns a name like `pg-primary` into an IP
address. You will add local name mappings in `/etc/hosts`. You will also test DNS
lookups. Getting names to resolve correctly is key for replication, backups, and
any setup where servers call each other by name.

**Time estimate:** 45 minutes

All steps run on your lab server. Connect with SSH first.

---

## 1. Why names instead of IP addresses?

IP addresses are hard to remember, and they change. Names like `pg-primary` or
`db.example.com` are steady and easy to read. But the network only understands IP
addresses. So something has to turn the name into an address every time you use
one. That step is called **name resolution**.

> **Concept - The Resolution Order:** When you use a name, Linux checks its
> sources in a set order. `/etc/nsswitch.conf` defines that order. On CentOS it is
> normally: first the local `/etc/hosts` file, then the DNS servers listed in
> `/etc/resolv.conf`. The first source with an answer wins. So a line in
> `/etc/hosts` beats DNS. You will use this fact all the time in labs.

---

## 2. /etc/hosts - Your local name table

`/etc/hosts` is a simple file that maps IP addresses to names. It is checked
before DNS. So it is the fastest way to give a server a name, with no DNS server
needed.

View the current file:

```bash
cat /etc/hosts
```

```
Expected output (yours will differ):
127.0.0.1   localhost localhost.localdomain localhost4 localhost4.localdomain4
::1         localhost localhost.localdomain localhost6 localhost6.localdomain6
```

Each line is `IP-address  name  [more-names]`. The first line is the reason the
name `localhost` always resolves to `127.0.0.1`.

To add an entry, edit the file with `vi`. This needs `sudo` because the file is
owned by root:

```bash
sudo vi /etc/hosts
```

Press `i` to enter insert mode, move to the end of the file, and add a line like:

```
10.0.1.51   pg-standby
```

This maps the name `pg-standby` to the IP `10.0.1.51`. Press `Esc`, then type
`:wq` and press Enter to save and quit.

Confirm the entry took effect by resolving the name:

```bash
getent hosts pg-standby
```

`getent hosts` looks up a name using the same resolution order the system uses.
So it respects `/etc/hosts`.

```
Expected output (yours will differ):
10.0.1.51       pg-standby
```

> **DBA Context - /etc/hosts in Replication:** In a two-node replication lab you
> put both nodes in each other's `/etc/hosts`:
> `10.0.1.50 pg-primary` and `10.0.1.51 pg-standby`. Then you set up replication
> with the names instead of IPs. If an IP changes, you fix one line in
> `/etc/hosts` instead of hunting through every config file. This is standard
> practice. You will do it in the replication module.

## 3. /etc/resolv.conf - Where DNS questions go

When a name is not in `/etc/hosts`, Linux asks a DNS server. The `/etc/resolv.conf`
file lists which DNS servers it asks.

```bash
cat /etc/resolv.conf
```

```
Expected output (yours will differ):
# Generated by NetworkManager
search ec2.internal
nameserver 172.31.0.2
```

- `nameserver 172.31.0.2` - the DNS server to ask. In AWS this is the VPC resolver
- `search ec2.internal` - a domain added to short names. If you look up `web`, it
  also tries `web.ec2.internal`

> **Concept - Do Not Hand-Edit resolv.conf:** On CentOS, NetworkManager usually
> generates this file. Manual edits get wiped out on the next network change or
> reboot. Read it to understand your DNS setup. But change DNS through
> NetworkManager, not by editing this file. Knowing it is auto-generated saves you
> from a confusing "my change disappeared" moment.

## 4. nslookup - Test a DNS lookup

`nslookup` asks a DNS server to resolve a name, then shows the answer. It is the
simplest way to test whether DNS is working.

`nslookup` and `dig` are not installed by default on a minimal CentOS Stream 9. Install them first:

```bash
sudo dnf install -y bind-utils
```

- `bind-utils` provides both the `nslookup` and `dig` commands.

```bash
nslookup github.com
```

```
Expected output (yours will differ):
Server:		172.31.0.2
Address:	172.31.0.2#53

Non-authoritative answer:
Name:	github.com
Address: 140.82.112.3
```

- `Server` - which DNS server answered (from `/etc/resolv.conf`)
- `Address: 140.82.112.3` - the IP the name resolved to

If DNS is broken, you get an error like `server can't find github.com` or the
command hangs and times out.

> **DBA Context - DNS and Backups:** Cloud backups often target a hostname, like
> an S3 endpoint or an off-site backup server. If DNS is failing, the backup job
> cannot resolve that name. It then fails with a confusing error that looks
> unrelated to DNS. When a backup or a remote connection breaks, `nslookup` the
> target name early. A DNS failure is easy to miss but quick to confirm.

## 5. dig - The detailed DNS tool

`dig` gives more detail than `nslookup`. It is the tool experienced admins reach
for. The `+short` option gives just the answer.

```bash
dig +short github.com
```

`+short` prints only the resolved addresses, nothing else.

```
Expected output (yours will differ):
140.82.112.3
```

For the full detail, run `dig` without `+short`:

```bash
dig github.com
```

```
Expected output (yours will differ):
; <<>> DiG 9.16.23-RH <<>> github.com
;; ANSWER SECTION:
github.com.		29	IN	A	140.82.112.3
;; Query time: 1 msec
;; SERVER: 172.31.0.2#53(172.31.0.2)
```

The `ANSWER SECTION` holds the result. `github.com` resolves to `140.82.112.3`.
The `A` means an IPv4 address record. The number `29` is the TTL, which is how
many seconds the answer can be cached.

> **Concept - hosts wins over DNS:** Remember the resolution order. Say you add
> `140.82.1.1 github.com` to `/etc/hosts`. Then `getent hosts github.com` returns
> your fake entry. But `dig github.com` still queries DNS and returns the real
> address. Why? `dig` and `nslookup` talk to DNS directly and skip `/etc/hosts`.
> But `getent` and normal programs follow the full resolution order. This
> difference explains many "it resolves one way but not the other" puzzles.
