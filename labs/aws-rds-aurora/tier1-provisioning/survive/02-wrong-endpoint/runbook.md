# Runbook: Wrong Endpoint
## Survive Scenario 02

**Symptom:** Application cannot start. DNS resolution failure for the database hostname.
**Severity:** Critical - application startup blocked
**Time to resolve:** 5 to 10 minutes

---

## Your Starting Point

A developer deployed a new version of the application. The config file was regenerated as part of the deployment. Now the application will not start.

Application logs show:
```
FATAL: Cannot connect to database
Error: could not translate host name
  "suta-rds-lab.XxXxXxXx.rds.amazonaws.com" to address:
  Name or service not known
```

The config file is at `/tmp/suta-app-config.env`.

---

## Step 1 - Read the Application Config

Look at what endpoint the application is trying to use:

```bash
cat /tmp/suta-app-config.env
```

Expected output (with injected wrong value):
```
# Application database configuration
# Generated by deploy pipeline
DB_HOST=suta-rds-lab.XxXxXxXx.rds.amazonaws.com
DB_PORT=5432
DB_NAME=labdb
DB_USER=postgres
```

The `DB_HOST` value does not look right.

---

## Step 2 - Test DNS Resolution for the Configured Host

Try to resolve the hostname in the config:

```bash
dig +short suta-rds-lab.XxXxXxXx.rds.amazonaws.com
```

Expected output when hostname does not exist:
```
(empty - no output)
```

No output means DNS could not find this hostname. The hostname is wrong.

---

## Step 3 - Find the Correct RDS Endpoint

List all RDS instances in your account and their endpoints:

```bash
aws rds describe-db-instances \
  --query "DBInstances[*].{ID:DBInstanceIdentifier,Endpoint:Endpoint.Address,Status:DBInstanceStatus}" \
  --output table
```

Expected output (yours will differ):
```
-----------------------------------------------------------------------------------
|                       DescribeDBInstances                                       |
+-------------------+--------------------------------------------+----------------+
|       ID          |                Endpoint                    |    Status      |
+-------------------+--------------------------------------------+----------------+
|  suta-rds-lab     |  suta-rds-lab.abc123xyz.us-east-1.rds.amazonaws.com | available |
+-------------------+--------------------------------------------+----------------+
```

The correct endpoint is: `suta-rds-lab.abc123xyz.us-east-1.rds.amazonaws.com`

Note the cluster identifier (`abc123xyz`) in the middle - it is different from what was in the config (`XxXxXxXx`).

---

## Step 4 - Verify the Correct Endpoint Resolves

Test the real endpoint:

```bash
dig +short suta-rds-lab.abc123xyz.us-east-1.rds.amazonaws.com
```

Expected output:
```
54.234.189.12
```

An IP address means the hostname resolves. Good.

---

## Step 5 - Test Port Connectivity

Confirm port 5432 is open at the correct endpoint:

```bash
nc -zv suta-rds-lab.abc123xyz.us-east-1.rds.amazonaws.com 5432
```

Expected output:
```
Connection to suta-rds-lab.abc123xyz.us-east-1.rds.amazonaws.com port 5432 [tcp/postgresql] succeeded!
```

---

## Step 6 - Fix the Config File

Update the config file with the correct endpoint:

```bash
CORRECT_ENDPOINT=$(aws rds describe-db-instances \
  --db-instance-identifier suta-rds-lab \
  --query "DBInstances[0].Endpoint.Address" \
  --output text)

echo "Correct endpoint: $CORRECT_ENDPOINT"
```

Update the file:

```bash
sed -i.bak "s|DB_HOST=.*|DB_HOST=${CORRECT_ENDPOINT}|" /tmp/suta-app-config.env
```

Verify the fix:

```bash
grep "^DB_HOST=" /tmp/suta-app-config.env
```

Expected output:
```
DB_HOST=suta-rds-lab.abc123xyz.us-east-1.rds.amazonaws.com
```

---

## Step 7 - Test the Connection Using the Fixed Config

Load the corrected config and try a psql connection:

```bash
source /tmp/suta-app-config.env

psql -h "$DB_HOST" -U "$DB_USER" -d "$DB_NAME" -p "$DB_PORT"
```

You will be prompted for the password. Enter it. Expected result:

```
psql (16.6)
SSL connection (protocol: TLSv1.3, ...)
labdb=>
```

Run a quick check:

```sql
SELECT current_database(), inet_server_addr();
\q
```

---

## Root Cause Summary

| | Detail |
|---|---|
| Root cause | Deployment pipeline wrote wrong endpoint to config (typo in cluster identifier) |
| Impact | Application could not start. Zero connections possible. |
| Database status | Instance was running fine the whole time |
| How to detect | DNS resolution fails ("Name or service not known") |
| Fix | Replace wrong hostname in config with the correct RDS endpoint |
| Time to fix | Under 5 minutes once you know to check the endpoint |

---

## Prevention

1. Store database endpoints in AWS Secrets Manager or Parameter Store. The application reads from there at startup, not from a config file that gets regenerated.

2. Validate config values in the CI/CD pipeline before deployment. Check that the hostname resolves with `dig` before shipping the config.

3. Use the RDS instance identifier, not the full endpoint, as the canonical reference. Derive the endpoint from the identifier at startup.

4. Write an integration smoke test that runs immediately after deployment and verifies the database connection before shifting traffic.
