# Secrets and Configuration as Code

This explains how a DBA keeps passwords out of code while still managing the database through
Terraform, and how database tuning becomes a reviewed file. Read it before the tutorial, where you
build both.

## The problem: databases need secrets, code is shared

A database needs a master password. A Terraform file is shared with the team, stored in Git, and
read by pipelines. If the password is typed into the file, it is now in every clone and every old
commit, forever. Deleting the line later does not help - Git remembers.

The rule: **never write a real secret in a `.tf` file.** Instead, let something else hold it and
let Terraform refer to it.

## Three safe places for a secret

- **Generated by Terraform** - the `random_password` resource makes a strong password nobody ever
  types or sees. This is how the tutorial creates the master password.
- **Stored in AWS Secrets Manager** - a managed vault. Terraform writes `{ username, password }`
  into it (as one JSON string), and applications read it at run time with IAM permission instead
  of a config file.
- **Supplied at run time** - a variable fed from an environment variable (`TF_VAR_db_password`)
  or a pipeline secret, so it never lands in a file.

## The part that surprises people: state

Terraform keeps a state file, its memory of what exists. If a resource has a `password`
attribute, **the password is written into the state file in clear text.** This is true even when
the value came from a vault.

- `sensitive = true` on a variable or output hides the value on your **screen** and in logs.
- It does **not** remove the value from the state file.

So the state file is as sensitive as the password itself. Store it in an encrypted, access-limited
remote backend, never in Git, and give very few people read access.

RDS has a stronger option: let AWS create and rotate the master password in Secrets Manager itself
(`manage_master_user_password`). Terraform then never holds the password at all.

## Reading a secret back

A secret can be read into Terraform with a **data source** (`aws_secretsmanager_secret_version`).
A data source only reads; it creates nothing. Three things go wrong with it, and each has a
different error:

- **ResourceNotFoundException** - the secret name or region is wrong.
- **AccessDeniedException** - the name is right but the IAM role may not read it. The fix is a
  permission, not a hardcoded password.
- **Invalid index** - the secret read fine, but your code asked for a JSON key that is not in the
  body. The secret body is a JSON string, so you decode it with `jsondecode()` and use exact key
  names.

Anything derived from a secret is sensitive, so Terraform forces `sensitive = true` on outputs
that expose it.

## Secret lifecycle details

- `recovery_window_in_days` controls how long a deleted secret can be recovered (7 to 30 days).
  The tutorial sets `0` (instant delete) only so labs clean up fast. In production leave the
  default.
- `name_prefix` adds a random suffix so a destroy-and-recreate does not collide with a secret that
  is still pending deletion.
- Rotating a password outside Terraform makes Terraform see a difference. Module 10 covers the
  `ignore_changes` rule that handles this.

## Configuration as code: the parameter group

Secrets are one kind of database setting. Tuning is the other. In RDS the instance reads its
PostgreSQL settings from a **parameter group**, and you write that group in Terraform:

- `family` must match the engine major version (`postgres16` for PostgreSQL 16).
- Each `parameter` block sets one value, for example `log_min_duration_statement = 500` logs every
  query slower than 500 milliseconds.
- Some parameters apply immediately; others only after a reboot. Terraform reports which.

The benefit is the same as for infrastructure: the tuning is reviewed, has history (who lowered
the slow-query threshold, and when), and is identical in dev and production.

## Habits to take with you

- Search for secrets before every commit (`grep -n 'password *= *"'`).
- If a secret ever reaches Git, **rotate it first**, then clean up.
- Treat the state file like a password vault.
- Prefer secrets read by IAM role over secrets copied into files.
