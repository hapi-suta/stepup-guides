# Oracle to EPAS Bridge - The Reference Document

## Why This Document Matters

This is the single most important document in the entire 8-week track.

You are an Oracle DBA. You have years of muscle memory and mental
models built around Oracle terminology, architecture, and tools. Every
time someone says something at Mastercard, your brain reaches for the
Oracle answer. That answer is now wrong, or only partially right.

This document gives you the EPAS equivalent for every Oracle concept,
tool, and command you have ever used. Read it. Print it. Tape it to your
monitor. Reference it 50 times a week. By week 8, you will not need it
anymore - the mappings will be in your muscle memory.

## 3. Transactions and Concurrency

This is the biggest architectural difference. Read carefully.

| Oracle Concept | EPAS Equivalent | Notes |
|:---------------|:----------------|:------|
| UNDO segments | (no equivalent) | PG keeps old row versions in the heap itself |
| Redo logs | WAL | Same purpose: durability + recovery |
| MVCC via UNDO | MVCC via heap (multiple row versions) | PG keeps xmin/xmax on every row |
| Read consistency (snapshot from UNDO) | Snapshot isolation (snapshot from row versions) | Same end result, different mechanism |
| READ COMMITTED isolation | READ COMMITTED isolation | PG default - same as Oracle default |
| SERIALIZABLE isolation | SERIALIZABLE isolation | PG uses SSI (Serializable Snapshot Isolation), can throw serialization errors |
| READ ONLY isolation | READ ONLY transaction | `SET TRANSACTION READ ONLY` |
| ORA-01555 "snapshot too old" | (different error) | PG cannot run out of UNDO. But xid wraparound is a real concern |
| Row-level locks (no escalation) | Row-level locks (no escalation) | Same behavior |
| Lock escalation | (none in PG either) | Both engines do not escalate locks |
| SELECT FOR UPDATE | SELECT FOR UPDATE | Same syntax |
| Deadlock detection | Deadlock detection | Same algorithm conceptually, deadlock_timeout parameter |
| VACUUM | VACUUM | **Required in PG** - reclaims space from dead rows. Autovacuum runs continuously. |
| ANALYZE | ANALYZE | Updates planner stats - autovacuum runs ANALYZE too |
| XID wraparound | XID wraparound | Real risk if autovacuum cannot keep up - 2 billion transaction limit |

**Critical mental model shift:** In Oracle, UPDATE rewrites the row and
puts the old version in undo. In PostgreSQL, UPDATE writes a NEW row
version (next to the old one) and marks the old one as "dead" via xmax.
Both rows live in the table file until VACUUM cleans up.

This means:

- Heavy update tables can bloat
- Long-running transactions block VACUUM (visibility horizon)
- You can never run out of UNDO space (because there is no UNDO)
- But you CAN run out of xid space if you never VACUUM (wraparound)

You will spend all of Module 05 on this.

## 5. High Availability and Disaster Recovery

| Oracle Concept | EPAS Equivalent | Notes |
|:---------------|:----------------|:------|
| Data Guard (Physical Standby) | Streaming replication + EFM | Streaming = the replication, EFM = the failover automation |
| Data Guard (Logical Standby) | Logical replication | Built-in since PG10 |
| Data Guard Broker | EFM (EDB Failover Manager) | Cluster management, automatic failover |
| Fast-Start Failover (FSFO) | EFM auto-failover mode | |
| Observer process | EFM witness node | Quorum + split-brain prevention |
| Switchover | EFM switchover | Planned role swap |
| Failover | EFM failover | Unplanned promotion |
| Maximum Performance mode | Async streaming replication | Default |
| Maximum Availability mode | Sync streaming replication (synchronous_commit=on) | |
| Maximum Protection mode | Sync streaming replication + synchronous_standby_names | |
| Active Data Guard (read on standby) | Hot Standby (default in PG) | Standby is readable by default |
| RAC (Real Application Clusters) | (no direct equivalent) | EPAS does not have shared-storage clustering |
| GoldenGate (logical multi-master) | EDB Postgres Distributed (PGD) | Multi-master with conflict resolution |

**Key insight:** Oracle separates "the replication" (Data Guard) from
"the management" (DG Broker). EPAS separates them too: streaming
replication is built into PostgreSQL, EFM sits on top to manage it.

You will use EFM in Module 07 and PGD in Module 11.

## 15. Gotchas - Things That Do NOT Map Cleanly

These are the places where your Oracle reflexes will mislead you. Pay
extra attention.

### Gotcha 1: There is no UNDO

PostgreSQL keeps multiple row versions in the table heap. There is no
undo tablespace, no undo retention, no ORA-01555. But VACUUM is now your
problem - if it falls behind, tables bloat. This is the #1 thing that
trips up Oracle DBAs new to PG.

### Gotcha 2: NULL handling differs

In Oracle, `'' = NULL` (empty string is NULL). In PostgreSQL, `'' != NULL`.
EPAS has a config parameter `edb_redwood_strings` that turns on Oracle
NULL/empty-string behavior. Check what Mastercard has set.

### Gotcha 3: Case sensitivity

Oracle stores identifiers UPPERCASE by default. PostgreSQL stores them
LOWERCASE by default. Unquoted identifiers are folded to lower in PG. If
you migrate an Oracle schema with mixed-case quoted identifiers, every
SQL query in your apps will need to quote them.

### Gotcha 4: TRUNCATE behavior

In Oracle, TRUNCATE is a DDL operation - cannot rollback. In PostgreSQL,
TRUNCATE is transactional - you CAN ROLLBACK a TRUNCATE.

### Gotcha 5: Implicit type conversion

Oracle is permissive about implicit conversions. PostgreSQL is strict.
`SELECT * FROM t WHERE id = '123'` works in Oracle (implicit cast), might
fail in PostgreSQL depending on the column type.

### Gotcha 6: Connection costs

In Oracle, opening a connection is cheap. In PostgreSQL, each connection
forks a new OS process - relatively expensive. ALWAYS use a connection
pooler (PgBouncer) in production. Mastercard almost certainly does.

### Gotcha 7: Index-Organized Tables

Oracle IOT has no PostgreSQL equivalent. CLUSTER on a table gives partial
benefit (physical sort by index) but is one-time, not maintained.

### Gotcha 8: Hierarchical queries

EPAS supports CONNECT BY (Oracle syntax). Community PG only supports
WITH RECURSIVE (SQL standard syntax). Code you write on EPAS that uses
CONNECT BY will not run on community PG.

### Gotcha 9: Default port

EPAS default port is **5444**. Community PG default port is **5432**.
Connection strings always need to be checked.

### Gotcha 10: Default service user

EPAS default service user is **enterprisedb**. Community PG default is
**postgres**. Many EDB docs assume `enterprisedb` user - watch for this.

### Gotcha 11: Database links

Oracle DB links are first-class. EPAS uses `postgres_fdw` (foreign data
wrapper) which is more limited and requires explicit foreign table
definitions. There is also `oracle_fdw` for reaching back to Oracle from
EPAS.

### Gotcha 12: SQL Plan Management

Oracle's SPM/baselines have no PG equivalent. If you absolutely need to
lock a query plan, use `pg_hint_plan` extension.

## 16. Mastercard Stack Mapping (Probable)

You have not seen Mastercard's actual stack yet, but based on EPAS +
EFM + Barman + PGD, this is what their production architecture probably
looks like:

```
                                    Application Tier
                                          |
                                          v
                                    PgBouncer (connection pooling)
                                          |
                                          v
                                    EFM-managed Cluster
                              +---+----+-----+----+----+
                              |        |          |
                          Primary   Standby    Witness
                          EPAS 16   EPAS 16    EPAS 16
                              |        |
                              |        | streaming
                              |        |
                              +---+----+
                                  |
                                  |  WAL archiving
                                  v
                              Barman backup server
                                  |
                                  v
                              S3 or NFS (long-term retention)

                          (separate cluster, may exist)

                                  PGD multi-master cluster
                              +--+----+----+----+
                              |       |        |
                          Region A  Region B  Region C
                          EPAS 16   EPAS 16   EPAS 16
                          (write)   (write)   (write)

                                  Monitoring
                                       |
                                       v
                              EDB PEM server (web console)
                                       |
                                       +-- collects from all DB hosts via PEM agent
```

Your job at Mastercard:

- Keep the EFM cluster healthy (Module 07)
- Keep Barman backups running and tested (Module 06)
- Respond to PEM alerts (Module 09)
- Maintain the PGD cluster if they run one (Module 11)
- Handle escalations from the migration team (Module 10)

You are not building any of this. You are operating it.
