# Scenario 07 - Shared Preload Libraries Crash

**Severity:** CRITICAL
**Expected Recovery Time:** 5-8 minutes
**Single Node:** NODE1 only

---

## Alert

```
ALERT: PostgreSQL failed to start.
The server was restarted and did not come back up.
systemctl status shows the service is not running.
Something in the configuration is preventing startup.
```

---

## Key Concepts for Revision

- **shared_preload_libraries** - This parameter specifies which libraries to load when PostgreSQL starts. Libraries are loaded into shared memory at server startup, before any connections are accepted. If a library does not exist or fails to load, PostgreSQL refuses to start entirely. This is a `postmaster` context parameter - it only takes effect on restart.

- **postgresql.auto.conf overrides postgresql.conf** - `ALTER SYSTEM SET` writes to `postgresql.auto.conf`, which takes precedence over `postgresql.conf`. If someone added a bad library via `ALTER SYSTEM`, the fix must target `postgresql.auto.conf`, not `postgresql.conf`.

- **PostgreSQL logs are your first stop** - When PostgreSQL fails to start, always check the logs first. The error message will tell you exactly which library failed to load. On CentOS with systemd, you can also check `journalctl -u postgresql-16` for the failure output.

- **Editing postgresql.auto.conf directly** - When PostgreSQL is down, you cannot use `ALTER SYSTEM` to fix the problem (because psql cannot connect). You must edit `postgresql.auto.conf` directly with a text editor. This is one of the few situations where direct file editing is the correct approach.

- **Common bad library scenarios** - A library might fail to load because: it was never installed (`CREATE EXTENSION` does not install the .so file), the package was removed during OS patching, the library was compiled for a different PostgreSQL major version, or someone typo'd the name.

## Diagnostic Steps

### Step 1 - Check if PostgreSQL is running

```bash
sudo systemctl status postgresql-16
```

Expected output (yours will differ):

```
● postgresql-16.service - PostgreSQL 16 database server
     Active: failed (Result: exit-code) since Sun 2026-04-19 ...
...
```

The status shows `failed` - PostgreSQL tried to start and could not.

### Step 2 - Check the PostgreSQL log for the error

```bash
sudo -iu postgres
```

```bash
cat /opt/pgsql/log/postgresql-$(date +%Y-%m-%d).log | tail -20
```

Expected output (yours will differ):

```
2026-04-19 10:55:01.234 UTC [5001]: [1-1] user=,db=,app=,client= FATAL:  could not access file "pg_fake_monitoring_lib": No such file or directory
2026-04-19 10:55:01.234 UTC [5001]: [2-1] user=,db=,app=,client= LOG:  database system is shut down
```

The `FATAL: could not access file "pg_fake_monitoring_lib"` tells you exactly which library is the problem.

### Step 3 - Check journalctl for additional context

```bash
exit
```

(`-u postgresql-16` = show logs for the postgresql-16 service only. `--no-pager` = print output directly instead of opening a scrollable viewer. `-n 20` = show the last 20 log lines.)

```bash
sudo journalctl -u postgresql-16 --no-pager -n 20
```

Expected output (yours will differ):

```
Apr 19 10:55:01 pg-primary postgresql-16[5001]: FATAL:  could not access file "pg_fake_monitoring_lib": No such file or directory
Apr 19 10:55:01 pg-primary systemd[1]: postgresql-16.service: Main process exited, code=exited, status=1/FAILURE
```

### Step 4 - Check what is in postgresql.auto.conf

```bash
sudo -iu postgres
```

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by ALTER SYSTEM command.
shared_preload_libraries = 'pg_stat_statements,pg_fake_monitoring_lib'
```

You can see the bad library `pg_fake_monitoring_lib` was added to the list.

```bash
exit
```

## Resolution

### Step 1 - Edit postgresql.auto.conf to remove the bad library

Since PostgreSQL is not running, you cannot use `ALTER SYSTEM`. Edit the file directly.

```bash
sudo -iu postgres
```

```bash
vi /opt/pgsql/data/postgresql.auto.conf
```

Find the line with `shared_preload_libraries` and remove `pg_fake_monitoring_lib` from the list. If the original value was `pg_stat_statements`, the line should read:

```
shared_preload_libraries = 'pg_stat_statements'
```

If `pg_fake_monitoring_lib` was the only library, remove the entire `shared_preload_libraries` line from the file.

Save and exit vi (`:wq`).

### Step 2 - Verify the file looks correct

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Confirm the bad library name is no longer present.

```bash
exit
```

### Step 3 - Start PostgreSQL

```bash
sudo systemctl start postgresql-16
```

### Step 4 - Verify PostgreSQL is running

```bash
sudo systemctl status postgresql-16
```

Expected output (yours will differ):

```
● postgresql-16.service - PostgreSQL 16 database server
     Active: active (running) since Sun 2026-04-19 11:00:05 UTC; 3s ago
...
```

### Step 5 - Verify shared_preload_libraries is valid

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d stepup_store
```

```sql
SHOW shared_preload_libraries;
```

Expected output (yours will differ):

```
 shared_preload_libraries
--------------------------
 pg_stat_statements
(1 row)
```

The value should contain only valid, installed libraries.

### Step 6 - Verify the database is functional

```sql
SELECT count(*) FROM pg_stat_user_tables;
```

Expected output (yours will differ):

```
 count
-------
     8
(1 row)
```

Exit psql.

```sql
\q
```

Exit the postgres user.

```bash
exit
```

## Interview Discussion Points

1. **What is the difference between shared_preload_libraries and session_preload_libraries?** - `shared_preload_libraries` loads libraries at server startup into shared memory - all backends share the loaded code. `session_preload_libraries` loads libraries when each new connection is created. A bad entry in `shared_preload_libraries` prevents the entire server from starting. A bad entry in `session_preload_libraries` only prevents new connections (existing connections keep working).

2. **How would you safely add a new extension to shared_preload_libraries in production?** - First, install the OS package (e.g., `dnf install pg16-pgaudit`). Then verify the .so file exists: `ls /usr/pgsql-16/lib/pgaudit.so`. Add the library via `ALTER SYSTEM SET shared_preload_libraries = 'existing_libs,new_lib'`. Schedule a maintenance window for the required restart. Have a rollback plan ready (the previous value).

3. **If PostgreSQL will not start and you cannot connect, what are your diagnostic tools?** - Log files in the log directory, `journalctl -u postgresql-16`, `pg_ctl status`, and direct inspection of configuration files (`postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf`). You can also try starting PostgreSQL in single-user mode (`postgres --single`) for some types of issues, but library loading failures happen before even single-user mode works.

4. **Can you test shared_preload_libraries changes without restarting?** - No. The libraries are loaded at startup and cannot be changed at runtime. However, you can check if a library file exists before adding it: `SELECT * FROM pg_available_extensions WHERE name = 'pgaudit'` checks if the extension is installed. But this only works while PostgreSQL is running.

5. **What monitoring would catch this before an outage?** - Monitor that PostgreSQL is running (basic process check). More importantly, use a configuration management tool (Ansible, Puppet) that validates `shared_preload_libraries` entries against installed packages before allowing a restart. Some teams also keep a "known good" copy of `postgresql.auto.conf` in version control.
