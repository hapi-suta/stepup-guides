# Scenario 04 - Sequential Scans Forced on Large Table

**Severity:** HIGH
**Expected Recovery Time:** 5-8 minutes
**Single Node:** NODE1 only

---

## Alert

```
ALERT: All queries are running slow.
Monitoring shows sequential scans on every table,
even tables with proper indexes.
A developer ran some 'optimization' commands
but won't say what they changed.
```

---

## Key Concepts for Revision

- **enable_indexscan and enable_bitmapscan are planner switches** - PostgreSQL has several `enable_*` GUCs (Grand Unified Configuration) that control whether the query planner considers certain access methods. When `enable_indexscan = off`, the planner will not generate index scan plans, even when an index exists and would be faster. When `enable_bitmapscan = off`, bitmap index scans are also excluded. With both off, the planner falls back to sequential scans for all queries.

- **These settings are meant for debugging, not production** - PostgreSQL provides these switches so DBAs can test how plans change when a particular access method is removed. They should never be set globally in production. A common mistake is someone testing query performance with `SET enable_indexscan = off` in a session and then accidentally persisting it with `ALTER SYSTEM`.

- **ALTER SYSTEM writes to postgresql.auto.conf** - `ALTER SYSTEM SET` writes to `postgresql.auto.conf`, not `postgresql.conf`. Settings in `postgresql.auto.conf` override `postgresql.conf`. This is why `grep enable_indexscan postgresql.conf` might not find the problem - you need to check `postgresql.auto.conf` as well.

- **pg_reload_conf() applies changes immediately for these settings** - Unlike `shared_buffers` which needs a restart, planner settings take effect after a `SELECT pg_reload_conf()` or `systemctl reload`. The `context` for these settings is `user`, meaning they can even be changed per-session.

- **EXPLAIN is your diagnostic tool** - `EXPLAIN (ANALYZE)` shows exactly which access method the planner chose. If you see `Seq Scan` on a table where you know an index exists, and the table has many rows, something is wrong with the planner configuration.

## Diagnostic Steps

### Step 1 - Check a query plan to confirm the problem

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d stepup_store
```

```sql
EXPLAIN (ANALYZE) SELECT * FROM orders WHERE customer_id = 1;
```

Expected output (yours will differ):

```
                            QUERY PLAN
-------------------------------------------------------------------
 Seq Scan on orders  (cost=0.00..250.00 rows=5 width=...)
   Filter: (customer_id = 1)
   Rows Removed by Filter: 9995
   Planning Time: 0.150 ms
   Execution Time: 15.200 ms
...
```

The planner chose `Seq Scan` even though an index on `customer_id` exists. This is the problem.

### Step 2 - Check if the index exists

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders' AND indexdef LIKE '%customer_id%';
```

Expected output (yours will differ):

```
        indexname          |                     indexdef
---------------------------+--------------------------------------------------
 idx_orders_customer_id    | CREATE INDEX idx_orders_customer_id ON ...
(1 row)
```

The index exists. The planner is choosing not to use it.

### Step 3 - Check the planner settings

```sql
SHOW enable_indexscan;
```

Expected output:

```
 enable_indexscan
------------------
 off
(1 row)
```

```sql
SHOW enable_bitmapscan;
```

Expected output:

```
 enable_bitmapscan
-------------------
 off
(1 row)
```

Both are disabled. This is the root cause.

### Step 4 - Find where the settings were changed

```sql
\q
```

Check `postgresql.auto.conf` - this is where `ALTER SYSTEM` writes:

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by ALTER SYSTEM command.
enable_indexscan = 'off'
enable_bitmapscan = 'off'
```

The settings were persisted via `ALTER SYSTEM`.

---

## Resolution

### Step 1 - Remove the bad settings with ALTER SYSTEM RESET

```bash
/usr/pgsql-16/bin/psql -p 5432 -d stepup_store
```

```sql
ALTER SYSTEM RESET enable_indexscan;
ALTER SYSTEM RESET enable_bitmapscan;
```

Expected output (for each command):

```
ALTER SYSTEM
```

This removes the lines from `postgresql.auto.conf`.

### Step 2 - Reload the configuration

```sql
SELECT pg_reload_conf();
```

Expected output:

```
 pg_reload_conf
----------------
 t
(1 row)
```

### Step 3 - Verify the settings are restored

```sql
SHOW enable_indexscan;
```

Expected output:

```
 enable_indexscan
------------------
 on
(1 row)
```

```sql
SHOW enable_bitmapscan;
```

Expected output:

```
 enable_bitmapscan
-------------------
 on
(1 row)
```

### Step 4 - Verify the query plan now uses an index

```sql
EXPLAIN (ANALYZE) SELECT * FROM orders WHERE customer_id = 1;
```

Expected output (yours will differ):

```
                            QUERY PLAN
-------------------------------------------------------------------
 Index Scan using idx_orders_customer_id on orders  (cost=...)
   Index Cond: (customer_id = 1)
   Planning Time: 0.100 ms
   Execution Time: 0.050 ms
...
```

The planner now uses an Index Scan. Execution time dropped significantly.

### Step 5 - Confirm postgresql.auto.conf is clean

```sql
\q
```

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

The `enable_indexscan` and `enable_bitmapscan` lines should be gone.

```bash
exit
```

## Interview Discussion Points

1. **What is the difference between enable_indexscan and enable_bitmapscan?** - `enable_indexscan` controls B-tree index scans where the index is traversed to find row pointers, then the heap is accessed one row at a time. `enable_bitmapscan` controls bitmap index scans where the index is scanned to build a bitmap of matching pages, then the heap pages are read in physical order. Bitmap scans are more efficient for medium-selectivity queries (returning 1-20% of rows) because they reduce random I/O. Disabling either one limits the planner's options.

2. **How would you detect this problem from monitoring alone?** - Watch for a sudden increase in `seq_scan` counts in `pg_stat_user_tables` relative to `idx_scan`. If `seq_scan` counts spike across all tables simultaneously, it points to a global setting change rather than a missing index on one table. Also monitor query latency - a sudden across-the-board slowdown suggests a global config change.

3. **Why does ALTER SYSTEM write to a separate file?** - `postgresql.auto.conf` is machine-managed. It separates human edits in `postgresql.conf` from programmatic changes via `ALTER SYSTEM`. This prevents `ALTER SYSTEM` from corrupting a hand-maintained config file. Settings in `postgresql.auto.conf` always override `postgresql.conf`, which is why checking only `postgresql.conf` can miss the problem.

4. **Could a connection pool or application-level SET cause the same symptoms?** - A session-level `SET enable_indexscan = off` affects only that session. If every connection in a pool inherits a bad setting (e.g., from `ALTER ROLE ... SET`), it could look global. Check `ALTER ROLE` settings with `SELECT rolname, rolconfig FROM pg_roles WHERE rolconfig IS NOT NULL;`. Also check `ALTER DATABASE ... SET` with `SELECT datname, datconfig FROM pg_database WHERE datconfig IS NOT NULL;`.

5. **When is it legitimate to disable index scans?** - For debugging: to see if a seq scan is actually faster for a specific query. For maintenance: during bulk loading, disabling index scans on the loading session can avoid overhead. For testing: comparing plan costs with and without index access. Always do this per-session with `SET`, never globally with `ALTER SYSTEM`.
