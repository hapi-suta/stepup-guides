# Guide 04 - Post-Upgrade Tasks

The upgrade is done but your work is not. A freshly upgraded cluster needs ANALYZE to rebuild optimizer statistics, extensions may need updating, and you should verify application connectivity before decommissioning the old cluster.

**Run on:** NODE1 only

---

## 1. Verify the Upgraded Cluster Starts Cleanly

After `pg_upgrade` completes, start the new cluster and confirm it is healthy.

SSH into NODE1.

```
ssh ec2-user@NODE1
```

For this guide, we use the upgraded cluster at `/opt/pgsql/data16` on port 5434 from Guide 02. Start it if it is not running.

```
sudo -iu postgres
```

```
/usr/pgsql-16/bin/pg_ctl -D /opt/pgsql/data16 -l /opt/pgsql/log/pg16-upgraded.log start
```

Expected output:

```
waiting for server to start.... done
server started
```

Confirm the version and that you can connect.

```
/usr/pgsql-16/bin/psql -p 5434 -c "SELECT version();"
```

Expected output (yours will differ):

```
                                                  version
-----------------------------------------------------------------------------------------------------------
 PostgreSQL 16.3 on x86_64-pc-linux-gnu, compiled by gcc (GCC) 11.4.1 20231218 (Red Hat 11.4.1-3), 64-bit
(1 row)
```

Check for any errors in the startup log.

```
exit
```

```
sudo tail -20 /opt/pgsql/log/pg16-upgraded.log
```

Expected output (yours will differ):

```
2024-10-15 14:23:11.402 UTC [1234] LOG:  starting PostgreSQL 16.3 on x86_64-pc-linux-gnu
2024-10-15 14:23:11.402 UTC [1234] LOG:  listening on IPv4 address "127.0.0.1", port 5434
2024-10-15 14:23:11.402 UTC [1234] LOG:  listening on Unix socket "/run/postgresql/.s.PGSQL.5434"
2024-10-15 14:23:11.431 UTC [1234] LOG:  database system was shut down at 2024-10-15 14:20:05 UTC
2024-10-15 14:23:11.435 UTC [1234] LOG:  database system is ready to accept connections
```

No ERROR or FATAL lines means a clean start.

## 2. ANALYZE All Databases

`pg_upgrade` does not transfer optimizer statistics. Running ANALYZE immediately after the upgrade is critical. Without it, the planner has no data to work with and will make poor query plans.

```
sudo -iu postgres
```

Run `vacuumdb` with `--analyze-in-stages` on all databases. This rebuilds statistics in three passes, starting with minimal statistics so the database is usable quickly, then building up to full statistics.

```
/opt/pgsql/data16/analyze_new_cluster.sh
```

(`analyze_new_cluster.sh` = generated by pg_upgrade. Runs vacuumdb in stages: first minimal stats for fast startup, then full stats for optimal plans.)

If the script is not present (for example, if you are doing a manual post-upgrade), run `vacuumdb` directly.

```
/usr/pgsql-16/bin/vacuumdb -p 5434 --all --analyze-in-stages
```

(`--all` = process every database. `--analyze-in-stages` = three-pass statistics collection: minimal, medium, then full. Equivalent to what analyze_new_cluster.sh does.)

Expected output (yours will differ):

```
vacuumdb: processing database "upgradetest": Generating minimal optimizer statistics (1 target)
vacuumdb: processing database "postgres": Generating minimal optimizer statistics (1 target)
vacuumdb: processing database "template1": Generating minimal optimizer statistics (1 target)
vacuumdb: processing database "upgradetest": Generating medium optimizer statistics (10 targets)
vacuumdb: processing database "postgres": Generating medium optimizer statistics (10 targets)
...
Done
```

> **Concept - Why Statistics Are Not Transferred**: Optimizer statistics are stored in `pg_statistic`, which contains histograms and correlation data about the actual data values in each column. These statistics are tied to internal OIDs that change during an upgrade. Transferring them directly would produce incorrect estimates. It is faster and more correct to rebuild them from scratch on the new cluster.

```
exit
```

## 3. Update Extensions

After a major upgrade, installed extensions may have newer versions available in PG16. List extensions that can be updated.

```
sudo -iu postgres
```

Check all databases for extensions with available updates. Start with the upgradetest database.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "SELECT name, installed_version, default_version FROM pg_available_extensions WHERE installed_version IS NOT NULL AND installed_version <> default_version;"
```

Expected output (yours will differ):

```
       name         | installed_version | default_version
--------------------+-------------------+-----------------
 pg_stat_statements | 1.9               | 1.10
(1 row)
```

Update each extension that has a newer version.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "ALTER EXTENSION pg_stat_statements UPDATE;"
```

(`ALTER EXTENSION ... UPDATE` = updates the extension to its latest available version. PostgreSQL runs the upgrade scripts (e.g. `pg_stat_statements--1.9--1.10.sql`) to migrate the internal catalog entries.)

Expected output:

```
ALTER EXTENSION
```

Verify the extension is now on the latest version.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "SELECT extname, extversion FROM pg_extension WHERE extname = 'pg_stat_statements';"
```

Expected output:

```
       extname        | extversion
----------------------+------------
 pg_stat_statements   | 1.10
(1 row)
```

> **Concept - Extension Version Upgrades**: Each extension ships with upgrade scripts named `extname--oldver--newver.sql`. When you run `ALTER EXTENSION UPDATE`, PostgreSQL finds the shortest upgrade path from your current version to the latest and runs the scripts in order. You do not need to specify the target version - PostgreSQL handles the path automatically.

Repeat the check for all other databases.

```
/usr/pgsql-16/bin/psql -p 5434 -d postgres -c "SELECT name, installed_version, default_version FROM pg_available_extensions WHERE installed_version IS NOT NULL AND installed_version <> default_version;"
```

Expected output:

```
 name | installed_version | default_version
------+-------------------+-----------------
(0 rows)
```

No extensions need updating in the postgres database.

```
exit
```

## 4. Verify pg_stat_statements is Working

`pg_stat_statements` collects query statistics. After an upgrade, verify it is collecting data correctly.

```
sudo -iu postgres
```

Check that pg_stat_statements is loaded.

```
/usr/pgsql-16/bin/psql -p 5434 -c "SHOW shared_preload_libraries;"
```

Expected output (yours will differ):

```
 shared_preload_libraries
--------------------------
 pg_stat_statements
(1 row)
```

If it is not in `shared_preload_libraries`, add it.

```
/usr/pgsql-16/bin/psql -p 5434 -c "ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements';"
```

Expected output:

```
ALTER SYSTEM
```

Then restart the cluster for the change to take effect.

```
/usr/pgsql-16/bin/pg_ctl -D /opt/pgsql/data16 restart -m fast
```

Expected output:

```
waiting for server to shut down.... done
waiting for server to start.... done
server started
```

Run a few queries to generate statistics.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "SELECT count(*) FROM employees;"
```

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "SELECT department, avg(salary) FROM employees GROUP BY department;"
```

Expected output (yours will differ):

```
  department  |         avg
--------------+---------------------
 Engineering  | 74998.5238095238095
 HR           | 75012.8181818181818
 Sales        | 75001.3333333333333
(3 rows)
```

Now check pg_stat_statements.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "SELECT query, calls, total_exec_time::int FROM pg_stat_statements ORDER BY calls DESC LIMIT 5;"
```

Expected output (yours will differ):

```
                          query                          | calls | total_exec_time
---------------------------------------------------------+-------+-----------------
 SELECT count(*) FROM employees                          |     1 |              45
 SELECT department, avg(salary) FROM employees GROUP ... |     1 |             120
(2 rows)
```

```
exit
```

## 5. Verify Application Connectivity

If your application uses a connection pooler or hardcoded connection string, test that it can connect to the upgraded cluster.

```
sudo -iu postgres
```

Test a connection using the unix socket (for local applications).

```
/usr/pgsql-16/bin/psql -h /run/postgresql -p 5434 -d upgradetest -c "SELECT 'connection ok';"
```

Expected output:

```
 ?column?
--------------
 connection ok
(1 row)
```

Test a TCP connection (for remote applications or connection poolers).

```
/usr/pgsql-16/bin/psql -h 127.0.0.1 -p 5434 -d upgradetest -c "SELECT 'tcp ok';"
```

Expected output:

```
 ?column?
----------
 tcp ok
(1 row)
```

Check pg_hba.conf is correct in the new cluster.

```
cat /opt/pgsql/data16/pg_hba.conf
```

Expected output (yours will differ):

```
# TYPE  DATABASE        USER            ADDRESS                 METHOD
local   all             all                                     trust
host    all             all             127.0.0.1/32            trust
host    all             all             ::1/128                 trust
```

> **Concept - pg_hba.conf After Upgrade**: `pg_upgrade` copies `pg_hba.conf` from the old cluster to the new one. Your authentication rules are preserved. However, if you initialized the new cluster from scratch (e.g. for the logical replication method), the new pg_hba.conf will be the initdb default. Always verify pg_hba.conf matches your application's auth requirements before switching traffic.

```
exit
```

## 6. Check for Incompatible Objects

`pg_upgrade` generates a log of any objects it could not handle. Check for warnings.

```
ls -la ~/pg_upgrade_output.d/
```

Expected output (yours will differ):

```
total 8
drwxr-xr-x. 2 postgres postgres  88 Oct 15 14:20 .
drwx------. 8 postgres postgres 141 Oct 15 14:20 ..
-rw-r--r--. 1 postgres postgres   0 Oct 15 14:20 dump_globals.log
-rw-r--r--. 1 postgres postgres   0 Oct 15 14:20 pg_upgrade_server.log
```

Zero-byte logs mean no issues.

```
sudo -iu postgres
```

```
ls -la ~/pg_upgrade_output.d/
```

Expected output (yours will differ):

```
-rw-r--r--. 1 postgres postgres   0 Oct 15 14:20 dump_globals.log
-rw-r--r--. 1 postgres postgres   0 Oct 15 14:20 pg_upgrade_server.log
```

If there are non-empty log files, read them.

```
cat ~/pg_upgrade_output.d/pg_upgrade_server.log
```

```
exit
```

## 7. Monitor for Performance Regressions

On the first day after an upgrade, watch for slow queries. Even after ANALYZE, some query plans may change between major versions due to planner improvements (or regressions).

```
sudo -iu postgres
```

Watch pg_stat_statements for the top time-consuming queries.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "SELECT query, calls, mean_exec_time::numeric(10,2) AS mean_ms, total_exec_time::numeric(10,2) AS total_ms FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;"
```

Expected output (yours will differ):

```
           query           | calls | mean_ms  | total_ms
---------------------------+-------+----------+----------
 SELECT department, avg... |     1 |   120.00 |   120.00
 SELECT count(*) FROM e... |     1 |    45.00 |    45.00
(2 rows)
```

If you find a slow query after upgrade, compare its plan to what it was on the old version. Use `EXPLAIN (ANALYZE, BUFFERS)` to capture the plan.

```
/usr/pgsql-16/bin/psql -p 5434 -d upgradetest -c "EXPLAIN (ANALYZE, BUFFERS) SELECT department, avg(salary) FROM employees GROUP BY department;"
```

Expected output (yours will differ):

```
                                                    QUERY PLAN
-------------------------------------------------------------------------------------------------------------------
 HashAggregate  (cost=2890.00..2890.03 rows=3 width=40) (actual time=48.201..48.202 rows=3 loops=1)
   Group Key: department
   Batches: 1  Memory Usage: 24kB
   Buffers: shared hit=540
   ->  Seq Scan on employees  (cost=0.00..2140.00 rows=100000 width=19) (actual time=0.013..21.847 rows=100000 loops=1)
         Buffers: shared hit=540
 Planning Time: 0.125 ms
 Execution Time: 48.235 ms
(8 rows)
```

```
exit
```

## 8. Remove the Old Cluster

Once you are satisfied with the upgraded cluster, remove the old cluster's data files to free disk space.

`pg_upgrade` generates a script to do this safely.

```
sudo -iu postgres
```

Check if the delete script exists.

```
ls /opt/pgsql/data16/delete_old_cluster.sh
```

Expected output:

```
/opt/pgsql/data16/delete_old_cluster.sh
```

Read the script before running it.

```
cat /opt/pgsql/data16/delete_old_cluster.sh
```

Expected output (yours will differ):

```
#!/bin/sh
rm -rf '/opt/pgsql/data15'
```

Run the delete script only after you are confident the upgrade is successful.

```
/opt/pgsql/data16/delete_old_cluster.sh
```

Verify the old directory is gone.

```
ls /opt/pgsql/data15
```

Expected output:

```
ls: cannot access '/opt/pgsql/data15': No such file or directory
```

```
exit
```

> **Concept - When to Delete the Old Cluster**: Wait at least 24-48 hours after cutover before running `delete_old_cluster.sh`. This gives you time to catch application errors or performance regressions before losing the ability to roll back. If you used `--link` mode, rolling back means your files are shared - take a backup before deleting. If you used `--copy` mode, you can start the old cluster again as long as you have not deleted it.

---

## Checkpoint

By the end of this guide, you should have:

- [ ] Started the upgraded PG16 cluster and verified no errors in the log
- [ ] Run ANALYZE on all databases using `analyze_new_cluster.sh` or `vacuumdb --analyze-in-stages`
- [ ] Updated extensions with `ALTER EXTENSION ... UPDATE`
- [ ] Verified `pg_stat_statements` is collecting data
- [ ] Tested application connectivity via unix socket and TCP
- [ ] Checked `pg_upgrade_output.d/` for any warnings
- [ ] Monitored query performance with `pg_stat_statements`
- [ ] Removed the old cluster using `delete_old_cluster.sh`
