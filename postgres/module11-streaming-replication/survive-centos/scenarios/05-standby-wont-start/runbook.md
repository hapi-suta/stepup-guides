# Runbook 05 - Standby Won't Start

**Severity:** High - No replication redundancy
**Time to resolve:** 5-10 minutes

---

## Fix Path

### Step 1: Attempt to start the standby

SSH to [NODE2] and try starting PostgreSQL:

```bash
sudo systemctl start postgresql-16
```

```bash
sudo systemctl status postgresql-16
```

You will likely see the service fail to start, or it starts as a primary (no standby.signal).

### Step 2: Check the PostgreSQL log for errors

On [NODE2], inspect the log:

```bash
sudo tail -50 /var/lib/pgsql/16/data/log/postgresql-*.log
```

Look for errors related to:
- Missing `standby.signal` file (PG starts as a primary instead of standby)
- Connection failures to the primary (bad primary_conninfo)
- "could not connect to the primary server" messages

> **Concept - standby.signal**: In PostgreSQL 12+, the presence of `standby.signal` in the data directory tells the server to start in standby (recovery) mode. Without it, the server starts as a standalone primary.

### Step 3: Recreate standby.signal

On [NODE2], create the missing file:

Switch to the postgres user:

```bash
sudo -iu postgres
```

```bash
touch /var/lib/pgsql/16/data/standby.signal
```

```bash
exit
```

### Step 4: Fix primary_conninfo in postgresql.auto.conf

On [NODE2], inspect the current setting:

Switch to the postgres user:

```bash
sudo -iu postgres
```

```bash
cat /var/lib/pgsql/16/data/postgresql.auto.conf
```

The `primary_conninfo` line will have incorrect connection details. Fix it:

```bash
psql -c "
  ALTER SYSTEM SET primary_conninfo = 'host=[NODE1] port=5432 user=replicator password=YOUR_REPL_PASSWORD application_name=standby1';
"
```

Or edit the file directly:

```bash
vi /var/lib/pgsql/16/data/postgresql.auto.conf
```

```bash
exit
```

> **Concept - postgresql.auto.conf**: This file stores settings made via `ALTER SYSTEM`. It is read after postgresql.conf and overrides any matching parameters. On a standby, primary_conninfo here controls where the WAL receiver connects.

### Step 5: Restart PostgreSQL

On [NODE2]:

```bash
sudo systemctl restart postgresql-16
```

Check the log again for successful startup:

```bash
sudo tail -20 /var/lib/pgsql/16/data/log/postgresql-*.log
```

Look for: "started streaming WAL from primary" or "redo starts at".

### Step 6: Verify standby is in recovery and streaming

On [NODE2], switch to the postgres user:

```bash
sudo -iu postgres
```

```bash
psql -c "SELECT pg_is_in_recovery();"
```

Expected: `t` (true).

Expected output (yours will differ):
```
 pg_is_in_recovery
-------------------
 t
(1 row)
```

```bash
exit
```

On [NODE1], switch to the postgres user:

```bash
sudo -iu postgres
```

Verify streaming:

```bash
psql -c "SELECT client_addr, state FROM pg_stat_replication;"
```

Expected output (yours will differ):
```
 client_addr  |   state
--------------+-----------
 10.0.1.52    | streaming
```

```bash
exit
```

Expected: `state` is `streaming`.

### Step 7: Verify data consistency

On both nodes:

```sql
SELECT count(*) FROM employees;
```

Counts should match.

## Key Concepts for Revision

- **standby.signal** replaced the old `recovery.conf` file in PostgreSQL 12. Its presence (even if empty) is the flag that tells the server to start in recovery mode.
- **primary_conninfo** is the libpq connection string the WAL receiver uses to connect to the primary. It must include host, port, user, and typically a password or reference to .pgpass.
- **postgresql.auto.conf** is auto-generated by ALTER SYSTEM commands. Manual edits are allowed but ALTER SYSTEM is safer because it handles quoting and syntax.
- **Recovery mode detection**: Use `pg_is_in_recovery()` to determine if a server is running as a standby. The presence of standby.signal alone is not sufficient - the server must also be running.
- **WAL receiver**: The standby spawns a WAL receiver process that connects to the primary's WAL sender. If primary_conninfo is wrong, the receiver cannot start, and replication stops.
- **pg_stat_wal_receiver** on the standby shows the connection status from the standby's perspective, including conninfo, last received LSN, and sender host.
- **Startup sequence**: PostgreSQL checks for standby.signal at startup. If found, it enters recovery mode and attempts to connect using primary_conninfo. Missing either one results in incorrect behavior.

## Interview Discussion Points

1. **Diagnosing startup failures**: Walk through your process for diagnosing why a PostgreSQL standby won't start. What logs do you check first? What are the most common causes?

2. **standby.signal vs recovery.conf**: Explain the transition from recovery.conf (PG 11 and earlier) to standby.signal + postgresql.auto.conf (PG 12+). Why was this change made?

3. **Security of primary_conninfo**: The primary_conninfo string often contains credentials. How do you manage this securely? Discuss .pgpass files, LDAP, certificate authentication, and secrets management.

4. **Standby starts as primary**: If standby.signal is missing and the standby starts as a standalone primary, what risks does this create? How do you detect and prevent split-brain?

5. **ALTER SYSTEM vs manual edits**: When should you use ALTER SYSTEM versus manually editing configuration files? What are the risks of each approach?

6. **Monitoring standby health**: What checks should run continuously to detect a standby that has silently stopped replicating? Discuss pg_stat_replication, pg_stat_wal_receiver, and lag-based alerts.

7. **Automation**: How would you automate the detection and repair of a misconfigured standby in a production environment? Where does configuration management (Ansible, Puppet) fit in?
