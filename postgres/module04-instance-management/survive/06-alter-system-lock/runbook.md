# Scenario 06 - ALTER SYSTEM Lock

**Severity:** MEDIUM
**Expected Recovery Time:** 3-5 minutes
**Single Node:** NODE1 only

---

## Alert

```
ALERT: PostgreSQL is running but performance is degraded.
The DBA team set tuning values in conf.d/tuning.conf but
shared_buffers shows 32MB instead of 256MB, and work_mem
shows 1MB instead of 16MB. Every query is being logged.
Something is overriding the conf.d settings.
```

---

## Key Concepts for Revision

Before diving into the fix, make sure you understand these concepts:

- **PostgreSQL configuration precedence** - PostgreSQL loads config files in a specific order: `postgresql.conf` first, then files included via `include_dir` (like `conf.d/`), and finally `postgresql.auto.conf`. The last value read wins. This means `postgresql.auto.conf` always overrides everything in `conf.d/` and `postgresql.conf`, because it is loaded last. This is by design - but it catches people off guard.

- **ALTER SYSTEM and postgresql.auto.conf** - `ALTER SYSTEM SET param = value;` writes to `postgresql.auto.conf`, not to `postgresql.conf`. It is a SQL command that modifies on-disk config without you editing files manually. The danger: these overrides are invisible if you only look at `postgresql.conf` or `conf.d/`. They persist across restarts.

- **pg_settings view** - The `pg_settings` system view shows every active parameter, its current value, AND its source. The `source` column tells you where the value came from (`configuration file`, `default`, `override`, etc.), and `sourcefile` tells you the exact file path. This is your single best tool for debugging "why is this value wrong?"

- **conf.d directory pattern** - Using `include_dir = 'conf.d'` in `postgresql.conf` lets you organize settings into separate files (e.g., `tuning.conf`, `logging.conf`). Files are loaded in alphabetical order. This is cleaner than one giant `postgresql.conf`, but you must remember that `postgresql.auto.conf` still loads after all `conf.d/` files.

- **Restart vs reload** - Most parameters can be changed with a reload (`pg_ctl reload` or `SELECT pg_reload_conf()`). But `shared_buffers` requires a full restart because it controls shared memory allocation, which is fixed at startup. Always check `pg_settings.context` to know whether a parameter needs reload or restart.

## Diagnostic Steps

### Step 1 - Check current parameter values

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW shared_buffers;"
```

Expected output (yours will differ):

```
 shared_buffers
----------------
 32MB
(1 row)
```

The value should be 256MB (from conf.d/tuning.conf), but it shows 32MB.

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW work_mem;"
```

Expected output (yours will differ):

```
 work_mem
----------
 1MB
(1 row)
```

Should be 16MB. Something is overriding conf.d.

### Step 2 - Find where the values are coming from

Use `pg_settings` to check the source of each parameter:

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SELECT name, setting, unit, source, sourcefile FROM pg_settings WHERE name IN ('shared_buffers', 'work_mem', 'log_min_duration_statement');"
```

Expected output (yours will differ):

```
             name             | setting | unit |       source       |               sourcefile
------------------------------+---------+------+--------------------+----------------------------------------
 log_min_duration_statement   | 0       | ms   | configuration file | /opt/pgsql/data/postgresql.auto.conf
 shared_buffers               | 4096    |  8kB | configuration file | /opt/pgsql/data/postgresql.auto.conf
 work_mem                     | 1024    | kB   | configuration file | /opt/pgsql/data/postgresql.auto.conf
(3 rows)
```

The key clue: `sourcefile` points to `postgresql.auto.conf`, not `conf.d/tuning.conf`. Someone used `ALTER SYSTEM` to set values that override the conf.d files.

### Step 3 - Inspect postgresql.auto.conf

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
shared_buffers = '32MB'
log_min_duration_statement = '0'
work_mem = '1MB'
```

There are the overrides. These were set with `ALTER SYSTEM` and they silently beat everything in conf.d.

### Step 4 - Confirm what conf.d has

```bash
cat /opt/pgsql/data/conf.d/tuning.conf
```

Expected output (yours will differ):

```
# Tuning parameters - set by DBA team
shared_buffers = '256MB'
work_mem = '16MB'
maintenance_work_mem = '128MB'
effective_cache_size = '768MB'
```

The conf.d values are correct - they are just being overridden.

```bash
exit
```

## Resolution

### Step 1 - Reset all ALTER SYSTEM overrides

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "ALTER SYSTEM RESET ALL;"
```

Expected output (yours will differ):

```
ALTER SYSTEM
```

This clears every entry from `postgresql.auto.conf`.

### Step 2 - Verify auto.conf is clean

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
```

The file should contain only the comment header now - no parameter overrides.

```bash
exit
```

### Step 3 - Restart PostgreSQL

A restart is required because `shared_buffers` cannot be changed with a reload.

```bash
sudo systemctl restart postgresql-16
```

### Step 4 - Verify correct values are active

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SELECT name, setting, unit, sourcefile FROM pg_settings WHERE name IN ('shared_buffers', 'work_mem', 'log_min_duration_statement');"
```

Expected output (yours will differ):

```
             name             | setting | unit |                sourcefile
------------------------------+---------+------+-----------------------------------------
 log_min_duration_statement   | -1      | ms   |
 shared_buffers               | 32768   | 8kB  | /opt/pgsql/data/conf.d/tuning.conf
 work_mem                     | 16384   | kB   | /opt/pgsql/data/conf.d/tuning.conf
(3 rows)
```

Now `sourcefile` points to `conf.d/tuning.conf` and `log_min_duration_statement` is back to the default (-1, meaning disabled).

### Step 5 - Confirm shared_buffers is 256MB

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW shared_buffers;"
```

Expected output (yours will differ):

```
 shared_buffers
----------------
 256MB
(1 row)
```

```bash
exit
```

## Interview Discussion Points

1. **What is the PostgreSQL configuration precedence order?** - PostgreSQL reads `postgresql.conf` first, then processes any `include` or `include_dir` directives (loading `conf.d/` files in alphabetical order), and finally reads `postgresql.auto.conf`. Within each file, if a parameter appears multiple times, the last occurrence wins. Since `auto.conf` is always read last, `ALTER SYSTEM` values always win. This is documented behavior but is the single most common source of "my config change didn't work" tickets.

2. **When should you use ALTER SYSTEM vs editing conf.d files?** - `ALTER SYSTEM` is best for quick, temporary overrides or when you need to change a setting without SSH access (you can run it over any psql connection). For permanent, version-controlled tuning, `conf.d/` files managed by Ansible or Terraform are better. The risk with `ALTER SYSTEM` is that it creates invisible overrides - months later, nobody remembers the ALTER SYSTEM was run, and conf.d changes mysteriously "don't work." Some teams disable ALTER SYSTEM entirely by revoking the privilege or setting `allow_alter_system = off` (PG17+).

3. **How would you audit what ALTER SYSTEM has changed?** - Read `postgresql.auto.conf` directly - it contains only ALTER SYSTEM changes. Or query `pg_settings WHERE sourcefile LIKE '%auto.conf%'` to find every parameter currently being overridden by auto.conf. In production, you should periodically audit this file. Some teams add a cron job or monitoring check that alerts if auto.conf has unexpected entries.

4. **What is the difference between ALTER SYSTEM RESET and ALTER SYSTEM RESET ALL?** - `ALTER SYSTEM RESET parameter_name` removes a single parameter from `auto.conf`, letting the value fall through to `conf.d/` or `postgresql.conf`. `ALTER SYSTEM RESET ALL` clears every entry from `auto.conf`. Use RESET ALL when you want to guarantee conf.d values are in control. Use RESET for a single parameter when other ALTER SYSTEM entries are intentional.

5. **Why does shared_buffers require a restart but work_mem does not?** - `shared_buffers` controls the size of PostgreSQL's shared memory segment, which is allocated once at server startup by the postmaster. Changing it requires deallocating and reallocating shared memory, which means stopping all backends - hence a restart. `work_mem` is a per-operation memory limit that each backend allocates from the OS heap as needed. It can be changed with a reload (or even per-session with SET), because no shared resource needs to be resized. The `pg_settings.context` column tells you: `postmaster` means restart required, `sighup` means reload, `user` means changeable per-session.
