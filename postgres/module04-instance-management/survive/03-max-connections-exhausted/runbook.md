# Scenario 03 - Max Connections Exhausted

**Severity:** HIGH
**Expected Recovery Time:** 5-10 minutes
**Single Node:** NODE1 only

---

## Alert

```
ALERT: Cannot connect to PostgreSQL.
All connection slots are in use.
Application servers report: FATAL: too many clients already
No new connections can be established.
```

---

## Key Concepts for Revision

Before diving into the fix, make sure you understand these concepts:

- **max_connections** - Controls the maximum number of concurrent connections PostgreSQL will accept. This includes all connections: application backends, background workers, replication connections, and superuser connections. When all slots are full, new connection attempts get `FATAL: too many clients already`. This is a postmaster-level parameter - changing it requires a restart.

- **superuser_reserved_connections** - Reserves a number of connection slots exclusively for superusers (users with the SUPERUSER attribute). The default is 3. This means if `max_connections = 100`, normal users can use up to 97 slots, and the last 3 are reserved for superusers. Setting this to 0 removes the safety net - if all slots fill up, even a superuser cannot connect to diagnose the problem.

- **pg_stat_activity** - A system view that shows one row per server process (connection). It includes the PID, user, database, query state, and the current query text. This is your primary tool for understanding who is using all the connections and what they are doing.

- **pg_terminate_backend() vs pg_cancel_backend()** - `pg_cancel_backend(pid)` sends a cancel signal to a query (the connection stays open). `pg_terminate_backend(pid)` kills the entire connection. When you need to free up connection slots, you need `pg_terminate_backend()` because canceling a query does not release the slot.

- **Connection pooling** - In production, you should never rely on `max_connections` alone for connection management. Tools like PgBouncer or Pgpool-II sit between applications and PostgreSQL, multiplexing many application connections into a smaller pool of database connections. This prevents connection exhaustion and reduces per-connection memory overhead.

## Diagnostic Steps

### Step 1 - Try to connect with psql

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb
```

Expected output:

```
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  too many clients already
```

You cannot connect. Every connection slot is in use.

```bash
exit
```

### Step 2 - Confirm PostgreSQL is running (not crashed)

```bash
sudo systemctl status postgresql-16
```

Expected output (yours will differ):

```
● postgresql-16.service - PostgreSQL 16 database server
     Active: active (running) since ...
```

PostgreSQL is running - it is just refusing new connections.

### Step 3 - Check the PostgreSQL logs for connection errors

```bash
sudo tail -20 /opt/pgsql/log/postgresql-*.log
```

Expected output (yours will differ):

```
FATAL:  too many clients already
FATAL:  too many clients already
...
```

Repeated "too many clients" messages confirm connection exhaustion.

### Step 4 - Check current max_connections setting from the config file

Since you cannot connect via psql, read the config files directly.

```bash
sudo -iu postgres
```

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
max_connections = '5'
superuser_reserved_connections = '0'
```

There are two problems: `max_connections` is set to only 5, and `superuser_reserved_connections` is 0 (no safety net for superusers).

```bash
exit
```

### Step 5 - Check how many backend processes are running

```bash
sudo ps aux | grep "postgres:" | grep -v grep | wc -l
```

Expected output (yours will differ):

```
8
```

This includes background workers plus the sleeping backends consuming all slots.

---

## Resolution

You have two options. Either terminate the sleeping backends and then fix the config, or fix the config and restart (which kills all connections).

### Approach A - Kill sleeping backends, then fix config

### Step 1 - Identify and kill the sleeping psql processes

```bash
sudo ps aux | grep "pg_sleep" | grep -v grep
```

Expected output (yours will differ):

```
postgres  12345  0.0  0.1 ... postgres: labdb postgres [local] active
postgres  12346  0.0  0.1 ... postgres: labdb postgres [local] active
...
```

### Step 2 - Kill all the sleeping backends

```bash
sudo kill $(ps aux | grep "pg_sleep" | grep -v grep | awk '{print $2}')
```

### Step 3 - Verify you can now connect

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SELECT count(*) FROM pg_stat_activity;"
```

Expected output (yours will differ):

```
 count
-------
     2
(1 row)
```

### Step 4 - Fix max_connections and superuser_reserved_connections

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "ALTER SYSTEM SET max_connections = 100;"
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "ALTER SYSTEM SET superuser_reserved_connections = 3;"
```

```bash
exit
```

### Step 5 - Restart PostgreSQL to apply the new limits

```bash
sudo systemctl restart postgresql-16
```

### Step 6 - Verify the new settings

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW max_connections;"
```

Expected output:

```
 max_connections
-----------------
 100
(1 row)
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW superuser_reserved_connections;"
```

Expected output:

```
 superuser_reserved_connections
--------------------------------
 3
(1 row)
```

```bash
exit
```

### Approach B - Edit auto.conf and restart (faster but drops all connections)

### Step 1 - Edit postgresql.auto.conf directly

```bash
sudo -iu postgres
```

```bash
vi /opt/pgsql/data/postgresql.auto.conf
```

Delete the `max_connections = '5'` and `superuser_reserved_connections = '0'` lines. Save and exit (`:wq`).

```bash
exit
```

### Step 2 - Restart PostgreSQL

```bash
sudo systemctl restart postgresql-16
```

This kills all sleeping backends and starts PG with the default `max_connections` from `postgresql.conf`.

### Step 3 - Verify settings and connectivity

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW max_connections; SHOW superuser_reserved_connections;"
```

```bash
exit
```

## Validation

Run the validation script to confirm the scenario is resolved.

```bash
./validate.sh
```

Expected checks:
- PostgreSQL is running
- PostgreSQL accepts connections
- max_connections is 100 or higher
- superuser_reserved_connections is at least 3
- No sleeping chaos backends remain
- postgresql.auto.conf has no max_connections = 5

## Interview Discussion Points

1. **Why is superuser_reserved_connections critical?** - Without reserved connections, a superuser has no way to connect and diagnose the problem when all slots are full. The default of 3 means that even when `max_connections - 3` slots are consumed by application traffic, a DBA with SUPERUSER can still get in to run `pg_stat_activity`, terminate runaway connections, or change settings. Setting this to 0 is never appropriate in production.

2. **How would you handle connection exhaustion in production without restarting?** - If `superuser_reserved_connections` is properly set, connect as a superuser and query `pg_stat_activity` to find the source. Look for idle connections that have been open too long (`state = 'idle'` with old `state_change`), long-running transactions, or connection leaks from a specific application. Use `pg_terminate_backend(pid)` to selectively kill connections. Then work with the application team to fix the leak.

3. **What is the memory impact of max_connections?** - Each connection consumes about 5-10MB of RAM for its backend process, plus `work_mem` for sorts/hashes per query. Setting `max_connections = 1000` means PostgreSQL might need 5-10GB just for connection overhead. This is why connection pooling is essential - PgBouncer can handle thousands of application connections using only 50-100 actual database connections.

4. **How does pg_isready behave when max_connections is exhausted?** - `pg_isready` returns success (exit code 0) because the server is technically accepting connections on the socket. It does not actually authenticate or consume a connection slot. This can be misleading in monitoring - a health check using `pg_isready` will report "OK" while applications cannot connect. Better monitoring uses an actual psql connection attempt.

5. **What is the difference between connection limiting at the role level vs. server level?** - `max_connections` is the server-wide ceiling. You can also set `CONNECTION LIMIT` on individual roles (`ALTER ROLE app_user CONNECTION LIMIT 20`), which limits how many connections that specific user can have. Both limits are enforced independently. Role-level limits help prevent one application from consuming all connections, but they do not protect against a bug in the application that opens hundreds of connections as the same user.
