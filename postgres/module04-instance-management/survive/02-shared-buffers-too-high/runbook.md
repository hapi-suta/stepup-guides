# Scenario 02 - Shared Buffers Too High

**Severity:** CRITICAL
**Expected Recovery Time:** 5-8 minutes
**Single Node:** NODE1 only

---

## Alert

```
ALERT: PostgreSQL failed to start. Service is DOWN.
A DBA ran ALTER SYSTEM to increase shared_buffers for
better cache performance. Now PG will not start.
```

---

## Key Concepts for Revision

Before diving into the fix, make sure you understand these concepts:

- **shared_buffers and shared memory** - `shared_buffers` controls how much memory PostgreSQL allocates for caching data pages in shared memory. This memory is allocated at startup using OS shared memory (POSIX `mmap` or System V `shmget`). If the requested amount exceeds what the OS can provide, PostgreSQL fails to start with a shared memory error.

- **ALTER SYSTEM and postgresql.auto.conf** - `ALTER SYSTEM SET parameter = value` writes to `postgresql.auto.conf`, which is a separate file from `postgresql.conf`. Settings in `postgresql.auto.conf` override everything in `postgresql.conf` and `conf.d/`. This file is machine-managed - you should not normally edit it by hand, but when PG cannot start, manual editing is your only option.

- **The 25% rule for shared_buffers** - A common guideline is to set `shared_buffers` to about 25% of total system RAM. On a 1GB server, that means roughly 256MB. Setting it to 64GB on a 1GB server is guaranteed to fail. PostgreSQL cannot start if the OS refuses the shared memory allocation.

- **Why PG cannot start means ALTER SYSTEM cannot fix it** - ALTER SYSTEM requires a running PostgreSQL connection. If PG will not start because of a bad `postgresql.auto.conf` value, you are locked out of SQL commands. The only fix is to manually edit `postgresql.auto.conf` on disk as the postgres OS user.

- **kernel.shmmax and shared memory limits** - On older kernels, `kernel.shmmax` capped the maximum shared memory segment size. Modern kernels (5.x+) with POSIX shared memory usually do not have this limit, but total RAM is still the hard ceiling. The error message will tell you exactly what limit was hit.

## Diagnostic Steps

### Step 1 - Check service status

```bash
sudo systemctl status postgresql-16
```

Expected output (yours will differ):

```
● postgresql-16.service - PostgreSQL 16 database server
     Active: failed (Result: exit-code) since ...
```

### Step 2 - Check PostgreSQL logs for the exact error

```bash
sudo tail -20 /opt/pgsql/log/postgresql-*.log
```

Expected output (yours will differ):

```
FATAL:  could not map anonymous shared memory: Cannot allocate memory
HINT:  This error usually means that PostgreSQL's request for a shared memory segment exceeded available memory, swap space, or huge pages.
LOG:  the database system is shut down
```

This tells you PostgreSQL tried to allocate more shared memory than the system has.

### Step 3 - Check how much RAM the server has

```bash
free -h
```

Expected output (yours will differ):

```
              total        used        free      shared  buff/cache   available
Mem:          968Mi       200Mi       500Mi        10Mi       267Mi       600Mi
```

The server has about 1GB of RAM. Requesting 64GB of shared_buffers is impossible.

### Step 4 - Inspect postgresql.auto.conf for the bad value

```bash
sudo -iu postgres
```

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
shared_buffers = '64GB'
```

There it is - `shared_buffers = '64GB'` is the problem.

```bash
exit
```

---

## Resolution

Since PostgreSQL is not running, you cannot use `ALTER SYSTEM RESET`. You must edit `postgresql.auto.conf` directly.

### Option A - Remove the bad line from postgresql.auto.conf (recommended)

### Step 1 - Edit postgresql.auto.conf as postgres user

```bash
sudo -iu postgres
```

```bash
vi /opt/pgsql/data/postgresql.auto.conf
```

Find the line:

```
shared_buffers = '64GB'
```

Delete it (position cursor on the line and press `dd`). Save and exit (`:wq`).

### Step 2 - Verify the file looks clean

```bash
cat /opt/pgsql/data/postgresql.auto.conf
```

Expected output (yours will differ):

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
```

The bad line should be gone.

```bash
exit
```

### Option B - Clear the entire auto.conf file

If you are unsure which lines are safe, you can truncate the file entirely. This removes all ALTER SYSTEM overrides and falls back to `postgresql.conf` and `conf.d/` values.

```bash
sudo -iu postgres
```

```bash
> /opt/pgsql/data/postgresql.auto.conf
```

```bash
exit
```

### Step 3 - Start PostgreSQL

```bash
sudo systemctl start postgresql-16
```

### Step 4 - Verify it started

```bash
sudo systemctl status postgresql-16
```

Expected output (yours will differ):

```
● postgresql-16.service - PostgreSQL 16 database server
     Active: active (running) since ...
```

### Step 5 - Check the current shared_buffers value

```bash
sudo -iu postgres
```

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SHOW shared_buffers;"
```

Expected output (yours will differ):

```
 shared_buffers
----------------
 128MB
(1 row)
```

The value should now come from `postgresql.conf` or `conf.d/` - something reasonable for the server's RAM.

### Step 6 - Confirm full functionality

```bash
/usr/pgsql-16/bin/psql -p 5432 -d labdb -c "SELECT count(*) FROM pg_stat_activity;"
```

Expected output (yours will differ):

```
 count
-------
     5
(1 row)
```

```bash
exit
```

## Interview Discussion Points

1. **Why can you not use ALTER SYSTEM RESET when PG fails to start?** - ALTER SYSTEM is a SQL command that requires an active connection to a running PostgreSQL server. If the server cannot start because of a bad value in `postgresql.auto.conf`, you have a chicken-and-egg problem. The only way out is to manually edit `postgresql.auto.conf` on disk. This is one of the few situations where directly editing that file is appropriate.

2. **What is the relationship between postgresql.conf, conf.d/, and postgresql.auto.conf?** - PostgreSQL reads them in order: `postgresql.conf` first, then any files included via `include_dir` (like `conf.d/`), then `postgresql.auto.conf` last. For any parameter that appears in multiple places, the last one wins. So `postgresql.auto.conf` always overrides everything else. This is why a bad ALTER SYSTEM value is particularly dangerous - it overrides whatever sane value you have in `postgresql.conf`.

3. **How would you set shared_buffers safely in production?** - First, check total RAM with `free -h`. Set `shared_buffers` to approximately 25% of total RAM (up to about 8GB for most workloads - beyond that, the OS page cache becomes more efficient). Use ALTER SYSTEM so the change persists and is clearly separated from the base config. Then restart PostgreSQL during a maintenance window. Monitor `pg_stat_bgwriter` afterward to see if the hit ratio improved.

4. **What is the difference between shared_buffers and the OS page cache?** - `shared_buffers` is PostgreSQL's own buffer pool - it reads data pages from disk into this cache and serves queries from it. The OS page cache is the kernel's file cache - it caches all file I/O transparently. Data often ends up in both caches (double buffering). That is why making `shared_buffers` too large wastes memory - you are stealing RAM from the OS page cache, which also helps PostgreSQL. The sweet spot is usually 25% of RAM.

5. **If you deleted the wrong line from postgresql.auto.conf, how would you recover?** - `postgresql.auto.conf` does not have a backup by default. If you accidentally remove a line you needed, you would have to re-apply it with ALTER SYSTEM after PG starts. A good practice is to always `cp postgresql.auto.conf postgresql.auto.conf.bak` before editing. Some teams use configuration management (Ansible, Puppet) to track these values, which provides a source of truth outside the file itself.
